# 车身朝向：改掉"两套方向"的根本矛盾

> 日期：2026-10-15
> 你反馈：**车头初始朝 X，但按 W 沿 Z 移动（也就是车头的左侧）**；Z/X 键也没效果

---

## 一、你这句话直接点出了根本矛盾

```
车头初始朝向 X
但 transform.forward 报告 Z
W 键沿 Z 移动 = 车头的左侧
```

也就是说**系统里存在两套"前方"**：

| 谁 | 认为前方是 |
|---|---|
| **模型的视觉车头** | **X** |
| **`transform.forward`（Unity 的"前方"）** | **Z** |
| 旧代码的移动方向 | 自己算的 `Quaternion.Euler(0,yaw,0) * Vector3.forward` → **Z** |

而旧代码是**分别**设置 `transform.rotation` 和计算移动方向 ——
两个量各自独立，一旦模型的视觉车头与 `transform.forward` 差 90°，
就必然出现"车头朝 X、却往 Z 走"。

## 二、我之前的修法方向都不对

| 我试过的 | 为什么没用 |
|---|---|
| 把 `roverYawOffset` 从 0 改成 90 | 只是改了**视觉旋转**，移动方向仍由 `Quaternion.Euler(0, yaw, 0) * forward` 独立算出 —— 两个量照旧错开 |
| 加 Z/X 运行时调偏移 | 同上的问题：调的是视觉，移动方向没跟着变 |
| 读 FBX 的 `FrontAxis = Z` | 那是**文件声明**，但模型内部实际转了 90°，声明与实现不符 |

**根因是"两套方向"，不是"偏移量数值不对"。**

---

## 三、这次的修法：让移动方向**就是**朝向

改成用 `transform.forward` 驱动移动：

```csharp
// 旧：自己算一个方向 + 另外设 rotation  → 两个量会错开
var dir = Quaternion.Euler(0f, roverYaw, 0f) * Vector3.forward;
rover.transform.rotation = Quaternion.Euler(0f, roverYaw + roverYawOffset, 0f);

// 新：朝向就是移动方向，从定义上不可能错开
var dir = rover.transform.forward * Mathf.Sign(forwardInput);
// 转向也直接转 rover 本体
rover.transform.Rotate(0f, turn * turnSpeed * dt, 0f, Space.World);
```

**这样"车头朝哪"和"往哪走"是同一个量** ——
不管模型内部怎么转，都不可能再出现"朝 X 却往 Z 走"。

### 那模型视觉车头与 forward 差的 90° 怎么办？

用**可视偏移**（`ApplyVisualYawOffset()`）处理：

```
rover（本体）         ← 语义正确：forward 就是移动方向
  └── 模型（子物体）   ← 额外转 roverYawOffset，把视觉车头掰到 forward 上
```

- **移动/转向** 用 `rover.transform`
- **视觉修正** 加在子物体上

两者职责分开，就不会互相干扰。

### 自动巡航同样改了

原来 auto 也是自己算一个方向再设 rotation（和 manual 各写一套）。
现在 auto 改成：
1. 让 rover 本体 `RotateTowards` 目标路点
2. 再沿自己的 `forward` 前进

**手动与自动共用同一套朝向语义**，不会一个对一个错。

### 诊断也改了

进入巡航时会打印：

```
[农场] 车身朝向诊断：
  roverYawOffset   = 0°　（按 Z/X 各转 90°）
  rover.forward    = (0.00, 0.00, 1.00)　主轴 Z
  可视模型 forward  = (1.00, 0.00, 0.00)      ← 与上面不一致，说明需要偏移
  ★ 移动方向 = rover.forward（现在两者是同一个量，不会错开）
  ★ 若「可视模型 forward」与 rover.forward 不一致，就调 roverYawOffset 直到重合。
  子物体数 = 1，可视节点 xxx
```

**判断方法变得很直接**：
- `rover.forward` 与 `可视模型 forward` **重合** → 对了
- 差 90° → 按 Z 或 X 调 90°
- 若打印「没有子物体」→ 说明模型没有子节点可以施加偏移，我就改用别的方式

## 四、Z / X 键为什么"没效果"

我查了：`HandleYawAdjustKeys()` 挂在两处 ——
`HandleShortcuts()`（空闲时）与 `HandleAutoShortcuts()`（自动巡航时），
**手动巡航时没有调用**。

而且旧实现里"偏移"只影响**视觉旋转**，所以即使按键生效，
**移动方向也不变** —— 你看到的当然还是"没效果"。**这才是它"没效果"的真实原因。**

现在：
- 偏移通过 `ApplyVisualYawOffset()` 生效，**每次都重新应用**（不依赖按键时机）
- 偏移只影响视觉，移动永远沿 `forward` —— 所以按 Z/X 时**能直接看到车头转正**

## 七、我的反思

我在这个问题上试了**四轮**（0 → 90 → 运行时按键 → 用 forward 驱动），
前三轮都在调"偏移量"，**而真正的根因是"系统里有两套方向"**。

你那句"车头朝 X、W 却往 Z 走"才是决定性线索 ——
它说明**不是数值不对，是结构不对**。

**教训**：当"某个量怎么调都不对"时，应该先问
"**是不是有两个量在各自为政**"，而不是继续调那一个量。
