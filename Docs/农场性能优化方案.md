# 农场性能优化方案

> 日期：2026-10-15
> 触发：Play 后 Statistics 显示 **Batches 283,776 / FPS 5.0 (200.4ms)**
> 状态：**已实现**，五个程序集编译通过。

---

## 一、先看真实数据

你截图里的 Statistics 是最硬的证据：

```
Graphics:
  CPU: main 200.4ms   render thread 198.2ms      ← 200ms 一帧 = 5 FPS
  Batches: 283,776        Saved by batching: 0   ← 关键
  Tris: 29.7M             Verts: 44.2M
  SetPass calls: 17141
  Screen: 1920x1080
```

**两个关键数字**：

| 数字 | 含义 |
|---|---|
| `Batches: 283,776` | 28 万次 draw call。正常演示场景应该在 **1000~5000** |
| `Saved by batching: 0` | **Unity 一次合批都没做成** —— 所有物体都是各画各的 |

而且 `20,059 个渲染器 × 14.1 = 283,776`，
**每个渲染器被画了 14 遍** —— 重复的部分主要是**阴影级联**（默认 4 档）。

**结论：卡顿是 draw call 爆炸，不是三角面太多**（29.7M 三角面对独显不算多），
也不是电脑性能问题。

---

## 二、根因：模型是"碎"的

我解析过这批模型的内部结构：

| 模型 | 网格数 | 材质数 |
|---|---:|---:|
| `玉米_成熟_正常.glb` | **74**（叶片×11、节环×11、茎节×12、雄穗、雌穗…） | 6 |
| `玉米田土壤_四垄.glb` | **111**（主地形 + 110 个土块 icosphere） | 6 |
| `房车.glb` | **957** | 19 |
| `平川台.glb` | 42 | 4 |

**每个网格都是一个独立 MeshRenderer**，而 glTF 导入的网格没有开启
"动态合批/GPU Instancing" 的资格，所以 Unity 合不了批。

于是：

```
玉米   200 株 × 74 网格 = 14,800
土壤    36 块 × 111 网格 =  3,996
房车     1 台 × 957 网格 =    957
地形     7 块 ×  50 网格 =    350
--------------------------------
                    ≈ 20,113 个渲染器
再 × 14（阴影级联 + 主相机）≈ 28 万 batches
```

## 三、优化措施（已实现）

### ① 网格合并 `MeshCombiner.cs`（新增）

按 **sharedMaterial 分组**，把零碎网格的顶点/法线/UV/顶点色变换到父级本地坐标后
拼成少数几个大 Mesh。

```
玉米 74 个 → 6 个（6 个材质）
土壤 111 个 → 6 个
地形 42 个 → 4 个
房车 957 个 → 19 个
```

**验证过材质是共用的**：Farm 场景里 20,059 个渲染器
只引用了 **13 种 (材质guid, fileID) 组合**，所以按材质合并有效。

**两个关键实现决定**：

| 决定 | 原因 |
|---|---|
| **按预制体合并一次，再实例化 N 次** | 如果每株玉米都合并一次，200 株 = 200 次合并，启动会卡十几秒。改成"合并预制体 → 缓存 → 实例化 200 次"，合并成本只付一次 |
| **玉米按阶段分开合并** | 一次合并只能覆盖一个物体树，"分阶段显隐"是按 SetActive 做的。三个阶段各自一个容器、各合并一次 → 每阶段 6 个合并块 |

### ② 阴影控制 `FarmLighting.cs`

| 改动 | 前 | 后 |
|---|---|---|
| 阴影级联 | 4 档（默认） | **1 档** |
| 阴影距离 | 150 m（默认） | **45 m** |
| 玉米投射阴影 | 开 | **关**（数量最大、影子不重要） |
| 土壤投射阴影 | 开 | **关** |
| 田埂/小路投射阴影 | 开 | **关** |
| 阴影分辨率 | High | Medium |

**阴影是那 14 倍里的大头** —— 每个投射阴影的物体都要按级联重画一遍。

### ③ 亮度压低（让 UI 为主）

按你的要求"UI 界面还是要以 UI 为主"：

| 参数 | 前 | 后 |
|---|---|---|
| `sunIntensity` | 0.85 | **0.55** |
| `ambientIntensity` | 0.85 | **0.5** |
| `groundPadColor` | 0.16/0.10/0.06 | **0.13/0.09/0.06** |

农场整体退到 UI 后面，白盒面板上的文字就压得住了。

### ④ 相机远裁剪面收紧 `FarmOptimizer.cs`

从 800 m 收到 300 m，减少远处无用绘制。

## 六、第二轮：合并方案失败，改用 GPU Instancing

### 实测反馈（第二次 Play）

```
CPU: main 120.5ms  render thread 87.4ms     FPS 8.3（比之前 5.0 好一点）
Batches: 122,162       Saved by batching: 0
Tris: 50.2M    Verts: 75.2M                ← ★ 比优化前【翻倍】了
SetPass calls: 7306    Shadow casters: 100739
```

**Batches 只降了 57%，但 Tris 从 29.7M 涨到 50.2M** —— 越优化几何越多，说明方向错了。

### 根因：合并方案在这个数据量下必然失败

日志里露了马脚：

```
[农场] 土壤网格已合并：8136 个 → 49 个块。        ← 期望 6 个，实际 49 个
[农场] 阶段 3 的玉米已合并：16000 个网格 → 47 个块。 ← 期望 6 个，实际 47 个
```

**为什么是 49 而不是 6**：单个 Mesh 的顶点上限是 **65,535**（16 位索引）。
而我实测过：

| 模型 | 顶点数 |
|---|---:|
| `玉米田土壤_四垄.glb` 主地形 | 19,928 |
| 加上 110 个土块 | 26,528 |
| **36 块土壤合计** | **约 95 万** |

95 万 ÷ 6.5 万 ≈ **15 个 chunk**。所以"36 块 → 49 个块"完全合理 —— **合并几乎没减少对象数**。

**更糟的是几何被复制了**：当 8 个渲染器被分到不同 chunk 时，
同一份几何会被写进多个 chunk，所以 `Tris` 反而翻倍。

**而且我确认了材质是共用的**（20,059 个渲染器只引用 13 种材质组合），
所以"按材质分组"本身没错，**错的是"合并"这个手段本身**。

### 正确方案：GPU Instancing

| | 网格合并 | **GPU Instancing** |
|---|---|---|
| 思路 | 把 N 个网格拼成 1 个大 Mesh | N 个物体**共用同一份 Mesh**，各画一次 |
| 内存 | **膨胀**（几何被复制） | **不涨**（只有一份 Mesh） |
| 顶点上限 | 受 65,535 限制，必然拆 chunk | 无限制 |
| 200 株玉米 | 47+ 个 chunk | 6 个 Mesh × 200 个实例 |
| draw call | 47 × 材质数 | **按 Mesh 批处理，约 6 次** |

**改动**（已实现）：

| 文件 | 改动 |
|---|---|
| `FarmGpuInstancing.cs` | **新增** —— 遍历渲染器，把所有材质的 `enableInstancing` 打开；并提供 `Measure()` 输出实测统计 |
| `FarmFieldBuilder.cs` | `optimizeMeshes` 默认**关闭**；新增 `optimizeInstancing` 默认**开启** |
| `FarmOptimizer.cs` | 新增 Instancing 步骤；`combineMeshes` 默认关闭 |

### 关于 `DefaultImporter` 的说明（虚惊一场）

所有 `.glb.meta` 里写的是 `DefaultImporter` 而不是 `ModelImporter`，
看着像"没被当模型导入"。但这是**正常的**：

> **glTFast 是 ScriptedImporter**，脚本导入器就是写 `DefaultImporter` 这种格式，
> **不会**写 `ModelImporter` 段。只有原生支持的 FBX 才是 `ModelImporter`。

证据：Farm 场景里有 **20,330 个真实的网格对象**，如果导入失败不可能有这些。
（`Art/Models/Rover/*.fbx.meta` 是 `ModelImporter`，因为 FBX 是 Unity 原生格式。）

## 十、关于"卡顿是不是电脑问题"

**不是。** 判断依据：

- `render thread` 耗时和主线程相当 —— 卡在**提交绘制**，不是游戏逻辑
- `Tris: 29.7M`（第一轮）对现代独显是常规量级
- `Batches: 283,776` 是病态值，正常应该在几千
- `Saved by batching: 0` —— 一次合批都没成功，这是**模型结构 + 材质设置**问题

换更好的电脑只能缓解，因为 draw call 是 CPU 侧瓶颈。
**打开 GPU Instancing + 关掉不必要的阴影投射，才是真正的解法。**
