# 项目执行流程

> 适用：本仓库（engineer，Unity 2022.3.62f2c1）的第一版 Demo 及其后续扩展
> 前置阅读：`Docs/Unity界面-方案分析.md`、`Docs/UI资源与字体评估.md`、`Docs/数值模拟验证记录.md`
> 本文回答一个问题：**要动工了，按什么顺序做、谁做什么、怎么不打架。**

---

## 第一部分：开工前必须先定的事

这三件事不定，后面所有工作都可能白做。**建议集中在一周内闭环。**

| # | 待定事项 | 谁来定 | 定不下来的后果 |
|---|---|---|---|
| 1 | **画风方向**：暖橙农业扁平风 / 冷蓝科技 HUD 风 | 策划 + 美术 | UI 素材无法筛选，做了要返工 |
| 2 | **数值规格冻结**：Ymax、单位、复合肥折算、pH 系数配比 | 策划 | 数值内核写不下去（见下节） |
| 3 | **字体方案**：继续用 `msyh SDF` / 换 Noto Sans CJK SC | 集成 | 换字体要重烘图集 + 改所有文本引用 |

### 数值规格需要冻结的最小集合

数值内核动工前，下列字段必须有确定值。建议做成一张表，策划签字后**冻结**，改要记录版本：

```
□ 五个适宜度函数的分段边界与保底值        ← 文档已有
□ 初始土壤各指标的取值范围（含单位）        ← 文档已有数值，缺单位
□ 推荐水肥方案总表（11 条规则）             ← 文档已有
□ 阶段消耗量表                            ← 文档已有
□ 指标演算公式（含系数）                    ← 文档已有，pH 系数配比待修
□ Ymax,geo 的具体数值                      ← 缺失
□ 各项指标的单位（mg/kg？g/kg？）           ← 缺失
□ 复合肥 → 氮磷钾的折算比例                 ← 缺失
□ 灌溉/施肥的成本参数（若收益要算钱）        ← 缺失
□ S1 判定条件的空洞如何补（"恰好 2 项 >0.6"）← 缺失
□ S3"任意项 0.6~0.8"是"至少一项"还是"所有项" ← 歧义
```

> **不要因为缺项就卡住开发。** 缺的项用**明确的占位值 + TODO 标记**先填上，写成配置表里的一个字段，后面改配置不改代码。关键是把它们**集中在一处**，而不是散落在代码里。

## 第二部分：开发顺序（这部分是核心）

### 核心原则：**数值内核最先做，UI 最后做**

理由很直接：

- 数值内核是**纯逻辑**，不依赖 Unity 渲染、不依赖美术、不依赖 UI
- 它能**在 Unity 外跑**（控制台程序/单元测试），几百次模拟几秒钟出结果
- **当前最大的风险就在数值**（施肥无效、pH 反向、判定空洞、缺参数）
- 如果在 Unity 里手动点着试数值，改一次配方要重新走一遍五阶段流程，效率差百倍

```
        ┌──────────────────────────────────────────────┐
        │  第 1 步：数值内核（纯 C#，Unity 外可测）      │
        │  ─ 五阶段模拟 / 适宜度 / 推荐 / 演算 / 产量    │
        │  ─ 输入配置表 → 输出每阶段完整快照             │
        └───────────────────┬──────────────────────────┘
                            │ 数值跑通、能批量验证
                            ▼
        ┌──────────────────────────────────────────────┐
        │  第 2 步：配置表（ScriptableObject / JSON）    │
        │  ─ 策划可改，不改代码                          │
        └───────────────────┬──────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
   ┌────────────────────┐      ┌────────────────────┐
   │ 第 3A 步：UI 框架   │      │ 第 3B 步：农场场景  │
   │ 状态机 + HUD 母版   │      │ 玉米田网格 + 机器人 │
   │ 12 屏界面           │      │ 巡航 + 相机         │
   └─────────┬──────────┘      └─────────┬──────────┘
             └─────────────┬─────────────┘
                           ▼
        ┌──────────────────────────────────────────────┐
        │  第 4 步：集成（串成完整五阶段循环）           │
        └───────────────────┬──────────────────────────┘
                            ▼
        ┌──────────────────────────────────────────────┐
        │  第 5 步：打磨（玉米长势表现 / 演示物料 / 优化）│
        └──────────────────────────────────────────────┘
```

**3A 和 3B 可以并行**（两个人各管一块），因为 UI 框架和农场场景几乎不重叠。

### 第 1 步：数值内核（详细）

**这是整个项目里最该先做、也最容易做对的部分。**

#### 架构：把数值和 Unity 彻底分开

```
Assets/Scripts/
├── Core/                          ← 纯 C#，不引用 UnityEngine
│   ├── SoilState.cs               土壤状态（5 动态 + 4 静态）
│   ├── Suitability.cs             五个适宜度函数
│   ├── WaterFertilizerPlan.cs     推荐水肥方案总表
│   ├── SoilAdvance.cs             阶段演算（下一阶段指标）
│   ├── YieldModel.cs              产量 / 收益计算
│   ├── SimConfig.cs               配置数据结构（纯数据类）
│   └── Simulation.cs              串起五阶段的总入口
├── Config/                        ← Unity 侧
│   └── SimConfigAsset.cs          ScriptableObject 包装 SimConfig
└── Gameplay/                      ← Unity 侧（后面才做）
```

**关键约束：`Core/` 里的代码一行都不许出现 `using UnityEngine;`。**

好处有三个：
1. 能写**单元测试**，不需要启动 Unity 就能验证数值
2. 能写**批处理脚本**（就像我做的 `model_probe.py`），一次跑上千组参数找问题
3. 核心逻辑不会被 MonoBehaviour 的生命周期搞乱

#### 交付物（第 1 步完成的标志）

- [ ] `Core/` 全部类实现完毕，无 UnityEngine 依赖
- [ ] 一份 `SimConfig` 的**默认配置**（把文档里所有表格填进去）
- [ ] 一个**编辑器窗口或控制台程序**，能输入初始土壤 + 每阶段水肥，输出五阶段完整过程
- [ ] **至少 20 组参数的批量验证结果**（证明数值行为符合策划预期）
- [ ] 单元测试覆盖：五个适宜度函数的边界值、演算公式、判定分支

#### 这一阶段要顺手验证的事

用批处理验证下面几点，有问题**现在就提给策划**，不要等 UI 做完：

1. 照抄推荐方案时的产量分布（是否集中在某个窄区间）
2. 施肥量/灌溉量从 0.5 倍到 3 倍，产量是否有区分度
3. 极端初始值（区间四个角）是否都能正常收敛
4. pH 是否会反向漂移
5. 有没有任何输入组合会走到"没有推荐方案"的分支

### 第 2 步：配置表

把文档里的表格搬成数据，**策划能自己改**。

| 配置项 | 来源 | 内容 |
|---|---|---|
| 适宜度函数参数 | TABLE 3–7 | 每个指标 5 个边界值 + 保底值 |
| 推荐水肥总表 | TABLE 13 | 11 条规则（条件 + 用量） |
| 阶段消耗量 | TABLE 18 | 4 阶段 × 3 元素 |
| 地形参数 | TABLE 0 | 名称、介绍、初始值区间、模型引用 |
| 作物参数 | TABLE 1 | 名称、介绍、**各指标最优区间**、模型引用 |
| 长势贴图 | 补充段 | 好/正常/差 三档 |
| 全局参数 | — | Ymax、土地面积、经济参数 |

**推荐形式：`ScriptableObject` + 一个导入脚本。**
策划维护 Excel/CSV，导入脚本一键生成 SO。这样：
- 策划改数值**不需要碰代码**，也不会产生代码冲突
- 数值改动有 diff 可查
- SO 之间用引用而不是字符串查找，不会因为改名字断链

> **注意**：TABLE 1 里"作物参数"目前只有文字介绍，**没有数值**。如果要扩展甜菜/红薯/土豆，每种作物都需要一整套最优区间 + 推荐方案表。这一条要提醒策划。

### 第 3A 步：UI 框架

#### 状态机设计

```
GameState:
  Welcome          初始界面（项目简介 / 开始体验）
  Intro            项目简介弹窗
  LandSelect       土地类型选择
  LandParams       土地基础数据设置
  PlantSelect      植物类型选择
  Confirm          确认选择
  FarmStage        农场主界面（S1–S5，含阶段推进）
  RobotCruise      机器人操控（手动 / 自动）
  Analyze          开始分析（建议 + 水肥输入）
  Revenue          收益计算
  Restart          开始新的模拟
```

- 一个 `GameFlowController` 持有当前状态，负责切换与参数传递
- 每个状态对应一个 `Screen` 预制体
- **所有"返回上一步"都走状态机**，不要各屏自己 `SetActive`

#### 必须一次定好的接口

| 接口 | 说明 |
|---|---|
| `IScreen.OnEnter(object args)` | 进入时接收参数 |
| `IScreen.OnExit()` | 离开时清理 |
| `GameContext` | 跨屏共享的数据（已选地形/作物/土壤状态/阶段） |

#### 12 屏的实现方式

概念层（前 6 屏 + 收获/收益）用一个**主 Canvas**，各屏是一个子节点，通过激活/禁用切换——**不要用 `SceneManager.LoadScene` 切场景**，因为切换会有加载黑屏且状态传递麻烦。

农场层（第 7–10 屏）另做一个 Canvas 叠在 3D 场景上，是 **HUD 覆盖**而不是独立场景。

#### 先做 HUD 母版

文档的 12 张图有一个共同结构：**左上操作提示 + 右上阶段状态 + 底部数据区 + 底部操作区**。

> **第一件事就是把这套布局做成一个预制体母版**，12 屏全部从它派生。

这一步做对了，后面 12 屏就是填内容。

### 第 3B 步：农场场景与机器人

| 任务 | 要点 |
|---|---|
| 玉米田网格 | 把田块切成 N×M 网格，每格记录 `bool 已探测` |
| 巡航覆盖判定 | 机器人挂球形触发器，进入网格则标记；统计已探测格数 → 覆盖率 |
| 自动巡航 | S 形路点走未访问格；走完切回按钮状态 |
| 手动巡航 | WASD 输入（**先定用旧 Input 还是新 Input System**）；相机跟随 |
| 数据逐条显示 | 探测数据按覆盖率阈值依次揭示，对应文档"随覆盖面积增加而按顺序更新" |
| 第三/第一人称 | 文档要求第三人称，但概念图是俯视——**要跟策划确认**（见方案分析文档） |

**相机方案建议**：做一个可切换的跟随相机（俯视 / 第三人称），默认俯视，按快捷键切换。这样两种理解都满足，成本也低。

### 第 4 步：集成

- 把所有 Screen 串起来，跑通**完整五阶段循环**
- 接通 `Core/` 的模拟结果 → UI 显示
- 接通玩家的水肥输入 → `Core/` 的演算
- 接通长势贴图切换

**集成的验收标准：从初始界面点到最后"开始新的模拟"，能完整走一遍且数据正确。**

## 第三部分：团队协作流程（Unity 特有）

**这部分是最容易出惨案的地方。** 场景和预制体是文本格式没错，但两个人同时改同一个场景，Git 几乎必然冲突，而且合并出来的场景可能悄悄坏掉。

### 铁律一：**按模块分场景，不按功能分**

```
Assets/Scenes/
├── Main.unity            ← 【集成负责人独占】正式演示场景
├── Dev_UI.unity          ← UI 负责人
├── Dev_Farm.unity        ← 农场/机器人负责人
└── Dev_Test.unity        ← 数值/联调测试用
```

- **每个人的开发和测试都在自己的 `Dev_*.unity` 里做**
- **绝不直接在 `Main.unity` 里改东西**
- 功能稳定后，做成**预制体**，由集成负责人拖进 `Main.unity`
- `Main.unity` **同一时间只有一个人能打开修改**

### 铁律二：预制体有主

| 预制体 | 归属 |
|---|---|
| `HUD_Master.prefab` | UI 负责人 |
| `Screen_*.prefab` | UI 负责人 |
| `FarmField.prefab` | 农场负责人 |
| `Robot.prefab` | 农场负责人 |

**非归属者只引用、不修改。** 需要改就在群里说，由归属者改。

### 铁律三：`ProjectSettings/` 改动要报备

`InputManager.asset`、`TagManager.asset`（新增 Tag/Layer）、`GraphicsSettings.asset` 这些**多人改动会互相覆盖**。

**规则：改这些之前先在群里说一声**，或者干脆指定一个人改。

### 铁律四：提交纪律

沿用 README 已有的两条：
- **动手前先 Pull，收工后立刻 Push**
- **先关 Unity 再提交**（Unity 运行时会持续改写 `.meta`）

补充一条：
- **提交前确认 `Main.unity` 能正常打开**（不要提交一个坏掉的主场景）

### 铁律五：资源改名要通知全员

**改文件名/移动位置 = GUID 变了 = 所有引用断裂。**

- 素材一旦被引用，**不要再改名、不要再移动**
- 必须改时，在群里发通知，让所有人 Pull 后重新确认引用

### 建议：定期集成日

**每周或每两周一个"集成日"**：所有人把自己的成果合进 `Main.unity`，跑一遍完整流程。

宁可频繁小规模集成，也不要最后一次性大合并——后者几乎必然出事。

## 第四部分：时间规划

按 **10~12 周，3~4 人**估算。人数少就按比例压缩范围（先砍扩展内容，不砍流程）。

| 周次 | 阶段 | 主要产出 | 里程碑 |
|---|---|---|---|
| W1 | 决策 | 画风定稿、数值规格冻结、字体定案 | ✅ 三件事闭环 |
| W1 | 安全网 | `.gitignore` 字体规则、目录规范、场景分工确定 | ✅ 不会踩合规/协作坑 |
| W2–W3 | 数值内核 | `Core/` 完成 + 批处理验证 + 单元测试 | 🎯 **数值跑通** |
| W3 | 配置表 | SO 配置 + 策划可改的工作流 | 🎯 策划能自己调数值 |
| W4–W6 | UI 框架 | 状态机 + HUD 母版 + 12 屏 | 🎯 12 屏可点击走通 |
| W4–W6 | 农场（并行） | 玉米田网格 + 机器人巡航 + 相机 | 🎯 巡航能采满数据 |
| W7–W8 | 集成 | 完整五阶段循环跑通 | 🎯 **Demo 可演示** |
| W9–W10 | 打磨 | 长势表现、文案、演示脚本、动画 | 🎯 演示流畅 |
| W11–W12 | 缓冲 | 修 bug、适配、录制 | — |

**关键里程碑是 W3（数值跑通）和 W8（Demo 可演示）。** 这两个点卡住要立刻缩减范围。

## 第六部分：`Assets/` 目录规范

**建议现在就定下来，越晚改成本越高。**

```
Assets/
├── Art/
│   ├── UI/              最终使用的 UI 贴图（含 Generic_UI 的 5 张）
│   ├── Models/          地形、房车、玉米、机器人
│   └── Materials/
├── Audio/
├── Fonts/               msyh SDF 等 TMP 字体资产
├── Scripts/
│   ├── Core/            纯 C# 数值内核（无 UnityEngine 依赖）
│   ├── Config/          ScriptableObject 配置
│   ├── Gameplay/        农场、机器人、相机
│   └── UI/              状态机与各屏
├── Prefabs/
│   ├── UI/
│   └── Gameplay/
├── Config/              SO 资产实例（策划改数值的地方）
├── Scenes/
│   ├── Main.unity       【集成独占】
│   └── Dev_*.unity      个人开发场景
└── UIresources/         【暂存】原始素材包，筛选后再移入 Art/
```

> `UIresources/` 是**素材仓库**，不是最终使用位置。筛选后的素材移到 `Art/UI/` 并**从此不再改名**。

## 第七部分：UI 素材后续扩充的处理约定

后续会加新素材。为了到时候能快速筛选，**现在定好取舍标准**。

### 筛选标准（按顺序判断）

| 顺序 | 检查项 | 不通过就淘汰 |
|---|---|---|
| 1 | **风格**：是否符合已定画风（暖橙农业 / 冷蓝科技） | 混风格必淘汰 |
| 2 | **语义**：元素含义是否与农业/数据演示冲突 | 武器/魔法/血条类淘汰 |
| 3 | **色调**：能否通过调色融入主色板 | 无法融入的淘汰 |
| 4 | **规格**：是否九宫格友好（边缘可拉伸） | 纯位图大图谨慎使用 |
| 5 | **授权**：是否允许再分发 / 商用 | 不明来源的淘汰 |
| 6 | **体积**：单张 >1 MB 的非必要贴图 | 考虑压缩或淘汰 |
| 7 | **必要性**：这个界面真的需要它吗 | 不需要的淘汰 |

### 素材入库流程

```
1. 新素材包放进 Assets/UIresources/<包名>/（保持原样，先不动）
2. 我列出全部内容 → 按上面 7 条标准分类（推荐用 / 可选 / 淘汰）
3. 你确认取舍
4. 选中的复制到 Assets/Art/UI/，按用途重命名，设好九宫格
5. 原始包可保留在 UIresources 或移出 Assets（决定权在你）
```

### 命名规范（建议）

```
<用途>_<样式>_<状态>.png

btn_primary_normal.png
btn_primary_hover.png
btn_primary_pressed.png
panel_dialog_large.png
frame_card.png
bar_progress_bg.png
bar_progress_fill.png
icon_back.png
```

**统一前缀便于在 Project 窗口用搜索快速定位**，也避免不同包的素材重名冲突。

## 第八部分：风险清单与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 数值太固定、玩家没决策空间 | 高 | 演示说服力弱 | **已定位根因**，先做数值内核验证，早改 |
| 两人同时改 `Main.unity` 冲突 | 高 | 场景损坏 | 按模块分场景，`Main.unity` 单人独占 |
| 中文字体缺字变方块 | 中 | 界面出现豆腐块 | 用 TMP，界面文案定稿后校验字符集 |
| `msyh SDF` 无法补字 | 中 | 新文案显示异常 | 存档源 TTF 到 `BlenderSources/fonts/` |
| 字体授权问题 | 低 | 竞赛合规风险 | 加 `.gitignore` 规则，或换 Noto |
| 素材风格不统一 | 中 | 画面"缝合感" | 先定画风样板图，再筛选素材 |
| 后期一次性大合并 | 中 | 大量冲突 | 每周集成日 |
| 美术资源改名导致引用断裂 | 中 | 场景变 Missing | 引用后不改名，改前通知 |
| 范围失控（想做 4 地形 4 作物） | 高 | 做不完 | **明确 Demo 只做平川台 + 玉米** |
