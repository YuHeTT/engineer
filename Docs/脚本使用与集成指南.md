## 一、三层结构与"谁能碰谁"

```
┌─────────────────────────────────────────────────────────────┐
│  Engineer.Core     （纯 C#，零 Unity 依赖，可独立测试）        │
│  ─ 数值逻辑：适宜度 / 推荐方案 / 演算 / 产量                   │
│  ─ 只依赖 System.*，编译期强制（asmdef: noEngineReferences）  │
└───────────────────────────┬─────────────────────────────────┘
                            │  单向依赖：Config / Editor → Core
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
┌────────────────────────┐          ┌──────────────────────────┐
│  Engineer.Config        │          │  Engineer.Editor         │
│  ─ ScriptableObject 包装 │◄─────────│  ─ 批量验证窗口           │
│  ─ 校验 / 导出 JSON      │  引用     │  ─ 仅编辑器编译           │
└────────────────────────┘          └──────────────────────────┘
        ▲
        │  未来：Gameplay / UI 引用 Core（或 Config）拿到配置
        │
┌───────┴─────────────────────────────────────────────────────┐
│  待建：Engineer.Gameplay（农场、机器人、相机）                 │
│  待建：Engineer.UI（状态机、12 屏）                            │
│  ─ 只做"读数据 + 送输入"，不放任何数值逻辑                      │
└─────────────────────────────────────────────────────────────┘
```

### 铁律

| 层 | 允许 | 禁止 |
|---|---|---|
| `Core` | `System.*`、纯 C# 类型 | `using UnityEngine` / `UnityEditor` / `Mathf` / `Debug.Log` |
| `Config` | Unity + Core | 写数值逻辑（逻辑一律放 Core） |
| `Gameplay` / `UI` | Unity + Core | **自己写适宜度公式、自己判断推荐方案** |

> **`UI` 层永远不要自己算适宜度。** 一切数值都从 `Simulation` 问。
> 判断标准：如果你在 UI 脚本里写了 `fPH * fOM * ...` 或者 `if (fN < 0.6)`，那就是写错地方了。

### 编译期保护

`Core/Engineer.Core.asmdef` 里 `"noEngineReferences": true` 意味着：
**在 `Core` 的任何文件里写一句 `using UnityEngine;` 都会编译报错。**
这不是靠自觉，是编译期强制的。想验证就执行 `Temp/compile-core.ps1`。

## 二、Core 怎么用

### 2.1 完整流程（最典型的用法）

```csharp
using Engineer.Core;

// ① 拿配置（唯一数据源，别自己 new 一堆常数）
SimConfig cfg = SimConfig.CreateDefault();

// ② 建模拟
var sim = new Simulation(cfg);

// ③ 初始化：玩家输入的土壤 + 静态指标随机
//    【注意】不传 rng 会自动新建，每次都不一样 —— 这正是要的效果
SoilState input = new SoilState
{
    pH = 6.9f, OM = 21.5f, N = 100f, P = 16.5f, K = 145f,
    // 静态四项不用填，Initialize 会按配置随机覆盖
};
sim.Initialize(input);
// 需要可复现（测试/批量验证）时：sim.Initialize(input, new System.Random(12345));

// ④ 逐阶段推进
while (!sim.IsFinished)
{
    // ---- 读当前状态，给 UI ----
    SoilState     soil = sim.CurrentSoil;        // 当前土壤（9 项）
    SuitabilityResult fit = sim.Evaluate();      // 五个适宜度
    RecommendedPlan   rec = sim.Recommend();     // 系统建议
    GrowthLevel      grow = sim.CurrentGrowth(); // 长势（切贴图用）

    bool docUndefined = sim.PlanTable.LastMatchUsedFallback;  // 该情况文档未定义

    // ---- UI 显示 fit / rec / grow / docUndefined，等玩家填水肥 ----

    // ---- 玩家提交 ----
    var applied = new FertilizerApplication(
        irrigation: 玩家填的灌溉量,
        organic:    玩家填的有机肥,
        n:          玩家填的氮肥,
        p:          玩家填的磷肥,
        k:          玩家填的钾肥);

    StageResult result = sim.Commit(applied);    // 结算并推进到下一阶段

    // result.SoilAfter 是下一阶段的土壤
    // result.Fit / result.Recommended / result.Growth 是本阶段的结果
}

// ⑤ 收益
RevenueReport report = sim.Revenue(area: 100f);  // 100 亩
```

**如果玩家点"采用系统建议"**，就一行：

```csharp
StageResult result = sim.Commit(rec.ToApplication(cfg));
```

### 2.2 各脚本的"使用姿势"

#### `SimConfig.CreateDefault()` — 配置

**整个工程唯一应该 `new` 出配置的地方。** 不要在 UI 或 Gameplay 里写 `0.2f`、`6.25f` 这类数字。

策划改了数值后，改这里或改 `SimConfigAsset`：

```csharp
var cfg = SimConfig.CreateDefault();
cfg.Yield.YmaxGeo = 1200f;                  // 改产量上限
cfg.Advance.pH_NCoef = 0.05f;               // 修 pH 反向问题
cfg.DynamicInputRanges[0].Max = 7.0f;       // 收窄 pH 输入上界
cfg.CompoundRatio = 1f;                     // 复合肥改成"14 就是氮14磷14钾14"
```

#### `Simulation` — 对外接口清单

| 成员 | 用途 |
|---|---|
| `Initialize(input, rng?)` | 开局。**只在这里和 `Commit` 里能改土壤** |
| `Evaluate()` | 当前五个适宜度 |
| `Recommend()` | 当前推荐方案（**永不返回 null**） |
| `CurrentGrowth()` | 当前长势等级 |
| `Commit(applied)` | 提交水肥，结算并推进 |
| `Revenue(area)` | 收益报告 |
| `CurrentStage` / `IsFinished` / `CommittedCount` | 流程状态 |
| `CurrentSoil` | 当前土壤（**只读语义，见下面的坑**） |
| `GetHistory(stage)` / `History` | 回看已结算阶段 |
| `PlanTable` | 拿规则表（`LastMatchUsedFallback`、`RulesOf`） |
| `DumpHistory()` | 导出全过程文本（日志、策划评审） |

#### `SuitabilityResult` — 适宜度

```csharp
fit.fpH / fit.fOM / fit.fN / fit.fP / fit.fK   // 单项
fit[SoilMetric.N]                              // 按指标取（静态项返回 1）
fit.StageFertility()                           // 阶段肥力系数（五项连乘）
fit.Min() / fit.Any(pred) / fit.All(pred)      // 条件判定用
```

**不要自己再写一遍分段函数。** 需要从土壤算适宜度就用：

```csharp
SuitabilityResult fit = SuitabilityResult.From(soil, cfg);
```

#### `RecommendedPlan` — 建议

```csharp
rec.Label              // "氮肥为主 + 磷肥"（UI 直接显示）
rec.Physiology         // 玉米生理说明（UI 直接显示）
rec.BaseIrrigation     // 单亩基准灌溉
rec.Amounts.Organic    // 各项用量（含 Compound 复合肥包装量）
rec.ToApplication(cfg) // 转成可提交的 FertilizerApplication（复合肥在此折算）
rec.ResolvedAmounts(cfg) // 只要肥料部分，且复合肥已折算（UI 显示用）
```

#### `StageResult` — 单阶段结果

```csharp
result.SoilBefore / result.SoilAfter
result.Fit / result.StageFertility / result.Growth
result.Applied / result.Recommended
result.EffectiveWaterRatio()            // 有效水比例，UI 可用于提示玩家
result.OverWaterRatio()                 // 超灌比例
result.DeviationFromRecommendation(cfg) // 玩家与建议的偏差
```

#### `RevenueReport` — 收益

```csharp
report.StageFertility      // 四阶段肥力系数（数组）
report.OverallFertility    // 平均肥力 Ffert
report.Yield               // 单位面积产量 Y
report.YmaxGeo             // 理论上限（界面可显示"满分"）
report.AchievementRate     // Y / YmaxGeo，界面的"达成率"
report.TotalYield          // 总产量 = Yield × Area
// 经济层（需策划给参数才有值）：
report.PricePerKg / report.TotalCost / report.GrossIncome / report.NetIncome
```

### 2.3 ⚠️ 使用时的坑

| 坑 | 说明 | 正确做法 |
|---|---|---|
| **`CurrentSoil` 是引用** | 直接改它等于改 `Simulation` 内部状态 | 要改就 `CurrentSoil.Clone()`；只读展示直接读没问题 |
| **`Evaluate()` 会重算** | 每次调用都重新过一遍曲线 | 一个阶段里调一次、存局部变量即可 |
| **`Initialize` 不传 rng 就随机** | 这是**对的**行为（G1 修复后） | 测试要可复现时显式传 `new System.Random(seed)` |
| **`PlanTable` 在构造时快照配置** | 构造后改 `cfg.PlanRules` 它不感知 | 配置定型后再 `new Simulation(cfg)` |
| **`Commit()` 后再读 `CurrentSoil` 已是下一阶段** | 容易搞混 | 本阶段数据从返回的 `StageResult` 里取 |
| **`Commit()` 在已结束时返回 null** | 循环里要先判 `IsFinished` | 用 `while (!sim.IsFinished)` |
| **玩家输入没有边界校验** | 负数会得到荒谬结果（见 H2） | UI 层自己 clamp，或等 Core 补 `InputLimits` |

## 三、Config 怎么用

### 3.1 在 Unity 里建配置资产

```
Project 窗口右键 → Create → Engineer → 数值配置
```

得到 `SimConfigAsset`。挂到场景里的某个 GameObject，或放进 `Resources/`。

```csharp
using Engineer.Config;

public class GameBootstrap : MonoBehaviour
{
    [SerializeField] private SimConfigAsset configAsset;

    private Simulation _sim;

    private void Awake()
    {
        SimConfig cfg = configAsset != null
            ? configAsset.BuildSimConfig()     // 用资产（含校验）
            : SimConfig.CreateDefault();       // 兜底：文档默认值
        _sim = new Simulation(cfg);
    }
}
```

**`SimConfigAsset` 的右键菜单**（在 Inspector 里右键组件）：

| 菜单项 | 作用 |
|---|---|
| 校验数值配置 | 打印错误与警告（错误必须修，警告是规则空洞） |
| 打印推荐方案表 | 按判定优先级列出 11 条规则 |
| 检查规则覆盖性 | 阈值采样约 25 万组 × 4 阶段，找判定空洞 |

### 3.2 配置与策划的工作流（建议）

```
策划维护 Excel / CSV          （Assets/Config/Source/*.csv）
        ↓  导入器（待做）
SimConfigAsset（ScriptableObject）
        ↓  BuildSimConfig()
SimConfig（纯 C#）
        ↓
Simulation
```

**为什么不让策划直接改 `ScriptableObject`**：SO 是二进制资产，Git diff 看不出改了什么，多人改还会冲突。CSV 能 diff、能用 Excel 改、冲突小。

`plan_rules.csv` 的列已经在 [数值内核与设计表实现方案.md](数值内核与设计表实现方案.md) 第 4.3 节设计好了，策划直接对着抄就行。

## 四、未来和哪些组件关联

### 4.1 与 UI 层（12 屏状态机）

**关联方式：UI 只读 `Simulation`，通过 `Commit` 送输入。**

```
GameFlowController（状态机）
   │ 持有
   ▼
GameContext（跨屏共享）
   ├─ Simulation sim
   ├─ SimConfig cfg
   ├─ TerrainDef 已选地形
   └─ CropDef    已选作物
   │
   ├──> WelcomeScreen        无数据依赖，纯展示
   ├──> IntroScreen          读 cfg 里的项目简介文案
   ├──> LandSelectScreen     读 cfg.Terrains（PlayableInV1 过滤）
   ├──> LandParamsScreen     用 cfg.DynamicInputRanges 生成滑条/输入框
   │                         → 产出 SoilState（前 5 项）
   ├──> PlantSelectScreen    读 cfg.Crops
   ├──> ConfirmScreen        回显地形 + 作物
   ├──> FarmStageScreen  ★   调 sim.Evaluate() / sim.Recommend() / sim.CurrentGrowth()
   ├──> RobotCruiseScreen    巡航覆盖率 → 探测数据（见 4.3）
   ├──> AnalyzeScreen    ★   显示 rec，收集玩家输入，调 sim.Commit()
   └──> RevenueScreen        调 sim.Revenue()
```

**关键接口建议**（UI 团队按这个写）：

```csharp
// 每个界面实现这个，由状态机驱动
public interface IScreen
{
    void OnEnter(GameContext ctx, object args);
    void OnExit();
}
```

`LandParamsScreen` 是最特殊的一个 —— 它需要把玩家输入**写回 `GameContext`**，
然后由 `FarmStageScreen` 第一次进入时调 `sim.Initialize(soil)`。

### 4.2 与农场场景 / 机器人

**关联点：巡航覆盖率。** 但目前 Core 里**没有**这个概念 —— 它属于 Gameplay 层。

```
FarmFieldController（玉米田网格）
   ├─ 把田块切成 N×M 网格，每格记 bool 已探测
   ├─ CoverageRatio => 已探测格数 / 总格数
   └─ RobotController 的球形触发器进入网格 → 标记

RobotCruiseScreen（UI）
   ├─ 读 CoverageRatio 显示进度条
   ├─ 按覆盖率阈值依次揭示探测数据（文档要求"随覆盖面积增加而按顺序更新"）
   └─ 点"更新数据"→ 用探测值覆盖原数据
```

**需要一个中间层**把覆盖率转成"探测到几条数据"：

```csharp
// 建议放在 Gameplay 层，不要放 Core（它是表现逻辑，不是数值逻辑）
public sealed class DetectionProgress
{
    public SoilMetric[] Order;          // 揭示顺序（文档说"按顺序更新"）
    public float[] RevealThresholds;    // 每条数据的揭示覆盖率，如 0.15/0.3/0.45...
}
```

**注意**：文档的设计意图是"原数据可能不准，所以要探测"，但**探测误差模型还没有设计**
（见 [漏洞与风险清单.md](漏洞与风险清单.md) I2）。当前探测值等于真值，等于没有信息增益。
这一块要等策划定义。

### 4.3 与玉米长势表现

`GrowthLevel` 已经和美术资源命名对齐了：

```csharp
GrowthLevels.AssetSuffix(GrowthLevel.Good)   // "好"
GrowthLevels.AssetSuffix(GrowthLevel.Normal) // "正常"
GrowthLevels.AssetSuffix(GrowthLevel.Bad)    // "差"
```

现有资源（`Assets/可能用到的建模/玉米与土壤_Blender模型_v1/`）命名是：

```
玉米_幼苗_好.glb  /  玉米_幼苗_正常.glb  /  玉米_幼苗_差.glb
玉米_成长_好.glb  /  玉米_成长_正常.glb  /  玉米_成长_差.glb
玉米_成熟_好.glb  /  玉米_成熟_正常.glb  /  玉米_成熟_差.glb
```

**注意阶段名与资源名的对应**（文档只说"第二三四阶段按长势切贴图"）：

| Stage | 文档阶段名 | 建议用的资源前缀 |
|---|---|---|
| S1 | 播种苗期 | **不显示植株**（文档："第一阶段只看的到土地"） |
| S2 | 营养旺长期 | `玉米_幼苗` 或 `玉米_成长` |
| S3 | 生殖关键期 | `玉米_成长` |
| S4 | 灌浆成熟期 | `玉米_成熟` |
| Done（收获期） | 收获期 | 与 S4 共用（文档明确） |

**这个对应关系需要策划确认**——三种资源前缀 vs 四个阶段，中间有个缺口。

### 4.4 与存档 / 回放（未来）

**不要直接对 Core 对象用 `JsonUtility`**。原因：

- `SuitabilityCurve` / `PlanCondition` / `PlanRule` 里有数组和对象引用
- `StageResult` 持有 `SoilState` 引用
- `Simulation` 里有 `PlanTable`（内含 `List<PlanRule>[]`），`JsonUtility` 处理不了

**正确做法**：写一个独立的 DTO 层做映射：

```csharp
[System.Serializable]
public struct SaveData
{
    public float pH, OM, N, P, K, Eh, BaseIon, As, Hg;
    public int currentStage;
    public float[] stageFertility;      // 已结算阶段的肥力系数
    public float[] appliedIrrigation;   // 每阶段玩家实际投入（回放用）
    public float[] appliedOrganic, appliedN, appliedP, appliedK;
}
```

### 4.5 与调试 / 演示工具

| 工具 | 现状 | 说明 |
|---|---|---|
| **数值批量验证窗口** | ✅ 已有 | 菜单 `Engineer / 数值批量验证` |
| `Simulation.DumpHistory()` | ✅ 已有 | 导出全过程文本，可直接贴给策划 |
| 阶段跳转（演示用） | ❌ 待做 | 演示时想直接跳到 S3，需要能在 `Simulation` 上"快进" |
| 实时数值覆盖显示 | ❌ 待做 | 开发期在屏幕上叠加显示 `Ffert` / 各适宜度 |

**阶段跳转的做法建议**：不要给 `Simulation` 加"跳转"接口（会破坏状态一致性）。
而是**用一个只读配置让所有阶段都用"照抄建议"快进**：

```csharp
// 演示用：快进到指定阶段
static void FastForward(Simulation sim, SimConfig cfg, Stage target)
{
    while (!sim.IsFinished && sim.CurrentStage != target)
        sim.Commit(sim.Recommend().ToApplication(cfg));
}
```

## 五、其他使用方式

### 5.1 只要算一次，不要状态机

不需要跑五阶段、只想算"这块地现在多少分"：

```csharp
var cfg = SimConfig.CreateDefault();

var soil = new SoilState { pH = 6.2f, OM = 18f, N = 75f, P = 12f, K = 130f };
var fit  = SuitabilityResult.From(soil, cfg);

Debug.Log($"Ffert = {fit.StageFertility():F4}");        // 阶段肥力系数
Debug.Log($"fPH={fit.fpH:F2} fN={fit.fN:F2}");          // 单项

var rec = new PlanTable(cfg).Match(Stage.S2, fit);      // 直接问 S2 的建议
Debug.Log(rec.Label + " / 水" + rec.BaseIrrigation);
```

**这个用法适合**：做数值调试工具、给策划做"输入土壤 → 看建议"的小工具。

### 5.2 只演算一步

```csharp
var next = SoilAdvance.Advance(
    current:     soil,
    stage:       Stage.S3,
    applied:     new FertilizerApplication(40f, 0f, 8f, 4f, 10f),
    recommended: rec,
    config:      cfg);
```

**适合**：做"如果我这样施会怎样"的预览功能（UI 上实时显示下阶段指标）。UI 里加个"预览"按钮，
玩家调滑条时就能看到下一阶段会变成什么样 —— **这个功能会明显提升演示体验**，成本很低。

### 5.3 批量扫描（不用开 Unity）

`Core` 是纯 C#，可以直接在控制台跑几千组参数：

```csharp
// 扫 100 组初始土壤，看产量分布
for (int i = 0; i < 100; i++)
{
    var sim = new Simulation(cfg);
    sim.Initialize(SoilGenerator.MakeAtRatio(cfg, i / 99f), new System.Random(i));
    while (!sim.IsFinished)
        sim.Commit(sim.Recommend().ToApplication(cfg));
    Console.WriteLine($"{i/99f:F2} -> {sim.Revenue().AchievementRate:P1}");
}
```

参考 `Temp/smoketest/SmokeTest.cs` 的写法，以及 `Temp/compile-core.ps1` / `Temp/run-smoketest.ps1`。

### 5.5 给策划的独立小工具（建议做）

一个编辑器窗口，**左边拖六条滑条**（pH / OM / N / P / K / 阶段），**右边实时显示**：

- 五个适宜度 + 阶段肥力系数
- 命中的推荐方案（含是否走了兜底）
- 下一阶段指标会变成多少

策划调数值时不用开 Unity 跑整个流程，几秒钟就能验证一个想法。**这是投入产出比最高的工具**，
大概 100 行代码，用的都是现成接口（5.1 + 5.2 的组合）。

## 六、扩展指引

### 6.1 加一个新土壤指标

以"加一个动态指标"为例：

1. `Foundation/SoilMetric.cs`：在枚举里**动态组末尾**加一项（**不能插在中间，会打乱下标**）
2. `Model/SoilState.cs`：加字段 + 在 indexer 的 switch 里加分支
3. `Model/SuitabilityResult.cs`：加字段 + indexer 分支 + `Min()` / `All()` / `Any()` / `Count()`
4. `Config/SimConfig.cs`：`Curves[]` 数组扩容 + 在 `CreateDefault()` 里加曲线参数

⚠️ **注意**：`Min()` / `Any()` 这类方法目前是**手写五项**的。加指标时容易漏。
如果要频繁加指标，建议改成遍历 `SoilMetrics.Dynamic` 数组 —— 但那样会有数组分配开销。
**当前只有 5 项，手写更快；加第 6 项时记得同步改这几处。**

### 6.2 加一种作物

1. `Config/SimConfig.cs` 的 `Crops[]` 里加 `CropDef`
2. 给该作物**独立的一套 `SuitabilityCurve[]`**（填进 `CropDef.Curves`）
3. 给该作物**独立的一套 `PlanRule[]`**（目前 `SimConfig.PlanRules` 是全局共享的，
   多作物时需要改成按作物分组 —— **这是当前架构需要改动的地方**）

⚠️ **这是个真实的架构限制**：现在 `SimConfig.PlanRules` 是全局的，只支持玉米。
要支持多作物，需要把 `PlanRules` 挪进 `CropDef`，或加一个 `cropId` 字段过滤。
**你已确认 v1 只做玉米**，所以现在不用改，但要知道这个点。

### 6.3 加一套地形

`Config/SimConfig.cs` 的 `Terrains[]` 里加 `TerrainDef`，把 `PlayableInV1` 设成 `true`。

⚠️ **但地形目前不影响任何数值**（只影响文案和模型）。
若要差异化，需要在 `SimConfig` 加"地形修正系数"，并让 `SuitabilityCurve` 或 `AdvanceCoef` 按地形取值。
**这是需要策划先定义的**。

### 6.4 调整数值（不写代码）

| 想改什么 | 改哪里 |
|---|---|
| 最优区间 / 保底值 | `SimConfig.CreateDefault()` 里的 `new SuitabilityCurve(...)` |
| 初始输入范围 | `DynamicInputRanges[]` |
| 静态指标随机范围 | `StaticRanges[]` |
| 推荐方案（用量/条件/优先级） | `BuildDefaultPlanRules()` |
| 阶段消耗量 | `StageConsumes[]` |
| 演算系数（含 pH 两个系数） | `AdvanceCoef` 的默认值 |
| 复合肥折算比例 | `CompoundRatio` |
| Ymax | `Yield.YmaxGeo` |
| 长势阈值 | `Growth.GoodAllAbove` / `BadAllBelow` |

**全部在 `Config/SimConfig.cs` 一个文件里。** 这是刻意的设计 —— 数值改动不该散落在各处。

## 七、开发期的两个验证手段

### 7.1 不启动 Unity 验证 Core（快）

```powershell
$src = Get-Content -LiteralPath 'Temp\compile-core.ps1' -Raw -Encoding UTF8
Invoke-Expression $src
```

输出：

```
Core 源文件数: 20
BCL 参考程序集数: 163
★ 编译通过：Core 确实不依赖 UnityEngine。
```

**这个脚本的价值**：它**完全不给任何 Unity 参考程序集**，
所以只要 `Core` 里出现 `using UnityEngine`，立刻编译失败。
这是"零依赖"的硬证据，不是靠人看。

⚠️ **局限**：它**只验证 `Core`**。`Config` 和 `Editor` 没有被验证 ——
本轮就是因为这个漏掉了 `Engineer.Editor.asmdef` 少引用 `Engineer.Config` 的错误。
**建议把脚本扩展到三个程序集**（需要额外提供 `UnityEngine.dll` / `UnityEditor.dll` 参考程序集路径）。

### 7.2 跑冒烟测试

```powershell
$src = Get-Content -LiteralPath 'Temp\run-smoketest.ps1' -Raw -Encoding UTF8
Invoke-Expression $src
```

**当前 32 项全绿**，覆盖：配置自检、曲线边界、规则覆盖、边界归属、长势判定、
静态指标随机性、完整流程、三条已知数值问题、复合肥折算。

### 7.3 Unity 内验证（必须做一次）

外部编译**不能替代** Unity 内编译。Unity 会额外检查：

- asmdef 引用关系是否成环
- `ScriptableObject` 的序列化字段
- `.meta` 与 GUID 一致性

**每次改完 asmdef 或加 `[SerializeField]`，都要在 Unity 里打开确认 Console 无报错。**

## 九、一句话总结

**用起来只有三个动作**：

```csharp
var cfg = SimConfig.CreateDefault();       // ① 拿配置
var sim = new Simulation(cfg);             // ② 建模拟
sim.Initialize(soil);                      // ③ 初始化
// 然后 while(!sim.IsFinished) { 读 Evaluate/Recommend/CurrentGrowth → 送 Commit }
```

**UI 层只需要记住两条**：

1. **一切数值从 `Simulation` 问**，不要自己写公式
2. **只通过 `Commit()` 送输入**，不要直接改 `CurrentSoil`

**最高优先级的三个待做**：

1. **CSV 导入器** —— 让策划能自己调数值（解锁 P0 的问题修复）
2. **策划数值工具窗口** —— 约 100 行，投入产出比最高（见 5.5）
3. **把编译验证扩展到三个程序集** —— 避免再踩 asmdef 漏引用
