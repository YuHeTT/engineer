## 一、本轮已改（先说清楚现状）

| 项 | 改动 | 结果 |
|---|---|---|
| 玉米株数 | `CornSpacing` 0.85 → **1.7** | 每块 10 垄 × 5 株 = **50 株/块，全田 200 株**（上一版 320，减少约 38%） |
| 边缘留空 | 新增 **`EdgeToEdgePlanting`**（默认开） | 首尾两株正好落在种植区的两条边界上，**实际间距自动摊开**，边缘不再留空 |

## 二、与 UI 连线方案

### 2.1 现状：农场和 UI 是两个独立场景

```
Assets/Scenes/UI.unity        ← 10 个界面状态、GameFlowController、GameSession
Assets/Scenes/Farm.unity      ← Sun / FarmCamera / FarmRoot（田块 + 玉米 + 田埂 + 地形）
```

两边通过 `FarmGrowthBinder` 间接联系：它 `FindObjectOfType<GameFlowController>()`
拿 `session`，再决定玉米显示哪个阶段。**独立跑 Farm 场景也能出画面**（就是没有阶段变化）。

### 2.2 三种合并方式（要选一个）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 加性加载**（推荐） | 新增 `Bootstrap.unity`，它加性加载 `UI` + `Farm` 两个场景 | 职责清楚、各自可单独调试、场景文件不互相污染 | 多一个场景，需要处理加载时机 |
| B. 并进 UI.unity | 把 `FarmRoot` / `Sun` / `FarmCamera` 拖进 UI 场景 | 最简单 | UI.unity 已 1.4 MB / 493 对象，再塞进来很臃肿；两个相机要处理 |
| C. 并进 Farm.unity | 把 `UI_Root` 拖进 Farm 场景 | 同理 | UI 已经调好，动它风险大（刚出过一次事故） |

**推荐 A。** 收益是：以后 UI 场景怎么改都不会影响农场，反之亦然。

`Bootstrap` 的职责很薄：

```csharp
// Bootstrap.cs —— 只负责把两个场景按顺序加载起来
IEnumerator Start() {
    yield return SceneManager.LoadSceneAsync("UI",  LoadSceneMode.Additive);
    yield return SceneManager.LoadSceneAsync("Farm", LoadSceneMode.Additive);
    // 把 FarmCamera 设为唯一激活的相机（UI 场景里的 Main Camera 要关掉）
    SceneManager.SetActiveScene(SceneManager.GetSceneByName("Farm"));
}
```

**要注意的一件事**：`UI.unity` 里已经有一个 `Main Camera`，
和农场场景的 `FarmCamera` 会冲突（两个相机同时渲染，画面会叠）。
加性加载后必须**停掉其中一个**（建议留 FarmCamera，UI 用 Overlay 模式配合）。

### 2.3 数据契约：谁需要读谁

```
                    GameSession（数值内核，Core 层，纯 C#）
                          ▲                    │
        写：Commit / 推进   │                    │ 读：阶段、长势、指标
                          │                    ▼
        ┌─────────────────┴────────┐   ┌──────────────────────────┐
        │  UI 层（10 个界面）        │   │  Farm 层（可视化）          │
        │  Analyze / Revenue / ...  │   │  FarmGrowthBinder         │
        └──────────────────────────┘   └──────────────────────────┘
                    ▲                              ▲
                    │                              │
                    └──── 巡航覆盖率 / 已探测指标 ────┘
                            （新数据，见 2.4）
```

**农场需要从 UI 拿到的东西**：

| 数据 | 现在从哪来 | 需要的改动 |
|---|---|---|
| 模拟是否开始 | `flow.Session.IsStarted` | 已有 ✅ |
| 当前阶段 S1~S5 | `session.UiStage` | 已有 ✅ |
| 长势（好/正常/差） | `session.Growth` | 已有 ✅ |
| **玩家选的亩数** | ❌ 还没有 | `GameContext` 要存"田块数"，农场读它调 `ApplyBlockCount` |
| **巡航覆盖率** | ❌ 还没有 | 见 2.4 |
| **已探测的指标** | ❌ 还没有 | 见 2.4 |

**UI 需要从农场拿到的东西**：

| 数据 | 用途 |
|---|---|
| 覆盖率（百分比） | 巡航界面显示"已探测 62%" |
| 已发现哪些格 | 分析界面决定哪些指标显示"已探测/未知" |
| 巡航是否完成 | 决定"进入分析"按钮是否可点 |

### 2.4 巡航 → 分析 的数据流（这是核心玩法链路）

策划文档里"探测误差"和"先探测后分析"是这个链路的骨架。现在的实现是空的，需要补：

```
玩家进 Farm 场景
   ↓
点「开始巡航」→ 切到 RobotCruise 状态
   ↓
机器人（胶囊体 + 球形触发器）按 S 形路点走
   ↓ 碰到的格子
GridCoverageTracker 标记该格「已探测」
   ↓ 实时
HUD 显示「已探测 12 / 36 格（33%）」
   ↓ 覆盖率 ≥ 阈值（比如 80%）或玩家手动结束
   ↓
分析界面：已探测的指标显示数值，未探测的显示「未探测」
                  ↑
         数值 = 真值 + 探测误差（SimConfig 里的 probeError）
   ↓
玩家调水肥 → 提交 → 回到农场，玉米换到下一阶段
   ↓ 重复 S2 / S3 / S4
收益界面
```

**要新增的三个类**（都在 `Assets/Scripts/UI/Farm/`）：

| 类 | 职责 |
|---|---|
| `FarmGridCoverage` | 把田块切成 N×M 网格，记录每格探测状态，算覆盖率 |
| `FarmCruiseController` | 机器人移动（手动 WASD / 自动 S 形路点）+ 球形触发器 |
| `ProbeResult` | 探测到的指标值（真值 + 误差），供分析界面读 |

**这里有一个要策划定的规则**：覆盖率到多少才算"可以分析"？
100% 太苛刻（玩家会嫌烦），我建议 **80% 可分析、100% 才给"完整数据"**。

### 2.5 阶段推进的视觉反馈

现在 `AnalyzeScreen` 提交水肥后会 `GoTo(FarmStage)`，玉米瞬间换成下一阶段。
**建议加一个过渡**：镜头缓推 + 玉米"长出来"（缩放缓动）。

成本很低（`FarmCameraRig` 加一个 `PlayStageTransition()`），但观感提升明显。

## 三、多亩数布局方案

### 3.1 核心规则：**1 块 = 1 亩 = 一块 12 × 9 m 的田**

玩家选亩数 → `ApplyBlockCount(n)` → 自动拆成行列 → 田块平铺 → 相机自动取景。
**每块田内部的种植密度不变**（都是 10 垄 × 5 株），
所以"亩数"纯粹是**块数**，和"每块种多密"解耦。这正好对上你定的
「玩家选择的亩数实际上是块数，1 块 = 1 亩」。

### 3.2 可选亩数与实际规模

按 `SplitIntoGrid`（优先接近 16:10 横屏比例，避免 16×1 那种长条）：

| 亩数 | 布局 | 整片田 (m) | 玉米株数 | 三角面约 | 备注 |
|---:|---|---|---:|---:|---|
| 1 | 1×1 | 13 × 10 | 50 | 39 万 | 单块，最清楚 |
| 2 | 2×1 | 27 × 10 | 100 | 78 万 | |
| **4** | **2×2** | **27 × 21** | **200** | **155 万** | **当前默认** |
| 6 | 3×2 | 41 × 21 | 300 | 233 万 | |
| 9 | 3×3 | 41 × 32 | 450 | 349 万 | 田开始大，要拉远 |
| 12 | 4×3 | 55 × 32 | 600 | 465 万 | |
| 16 | 4×4 | 55 × 43 | 800 | 620 万 | 需要 LOD，见 3.4 |

**可选范围**：`FarmVisualConfig.SelectableBlockCounts = { 1, 2, 4, 6, 9, 12, 16 }`。
我建议 UI 上就用这几个（都能拆成规整的行列），**不要给任意数字**
（比如 7 会变成 7×1 的长条，很难看）。

### 3.3 相机怎么跟着变

`FarmCameraRig.FrameField(bounds)` 已经能按包围盒自动取景，**链路要接上**：

```csharp
config.ApplyBlockCount(selectedBlocks);
fieldBuilder.Build();
paths.Build();
rig.FrameField(fieldBuilder.FieldBounds);   // ← 这一步现在没接
```

但**光拉远不够**：16 亩时田有 55 m 宽，拉到能看全，
单株玉米就只剩几个像素，画面变成"一片绿糊"。

**建议做三档取景**（`FarmCameraRig` 加一个 `ViewLevel` 枚举）：

| 档 | 看什么 | 相机 | 适合 |
|---|---|---|---|
| **全景** | 整片田的户型、田埂、小路 | 高、俯角大 | 展示"我选了多大一片地" |
| **中景**（推荐默认） | 一个田块 + 相邻边界 | 中等高度 | 日常操作、看玉米长势 |
| **近景** | 单株玉米细节 | 贴近 | 展示"长势好坏"的对比 |

按 Tab 循环切换，或者按亩数自动选默认档（亩数大 → 默认中景）。

### 3.4 大亩数的性能方案

**四层降级**，按需启用：

| 层 | 做法 | 触发条件 |
|---|---|---|
| L1 相机裁剪 | Unity 自带的 frustum culling，远景自动不画 | 一直开 |
| L2 玉米 LOD | 远处用低面数代理（4 层面片十字交叉），近处用真模型 | 亩数 ≥ 9 |
| L3 土壤代理 | 土壤块远处换成一个平面 + 贴图（省掉 1.25 万面/块） | 亩数 ≥ 12 |
| L4 分块加载 | 只加载相机附近的田块 | 亩数 ≥ 16 |

**实测数**：土壤块 12,520 面/块 × 9 块/亩 = **11.3 万面/亩**，
玉米（成熟正常）约 5,500 面/株。
所以 **4 亩 155 万面、16 亩 620 万面** —— 后者的瓶颈其实是**土壤块**，不是玉米。

**建议先只做到 L2**，并把"可选亩数"上限设成 **9**。理由：
- 9 亩 349 万面，现代独显能跑
- 演示场景不需要 16 亩，"9 亩"听起来也够意思
- L3/L4 要改数据结构和加载逻辑，成本高、收益低

| # | 内容 | 依赖 | 估时 |
|---|---|---|---|

| **7** | 房车接入（`智能农田房车_精细可开合_v2.glb`，含开合动画） | 无 | 0.5 天 |
| **8** | 阶段推进的视觉过渡 | 6 | 0.5 天 |

这是整个 demo 最能体现"数字孪生"的地方。

**第 5、6、8 步是连接性的活**，做完农场和 UI 就是一体了。
