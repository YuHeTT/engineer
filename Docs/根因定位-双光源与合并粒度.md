# 根因定位（第三版，这次有确凿证据）

> 你提供的转储让我确认了两件事，并推翻了我上一个结论。

## 一、我上一个结论是**错的**

我写的是"RenderSettings 是 per-scene 的，所以激活场景不对"。
虽然那句话本身没错，但**你转储里真正暴露的问题更简单、更直接**：

```
太阳 : Directional Light（intensity=1, shadows=Soft）
```

**我们的太阳叫 `Sun`，不叫 `Directional Light`。** 我去查了场景：

```
=== UI.unity ===
   GO Directional Light   active=1     ← ★ UI 场景自带一个平行光
   平行光组件数: 1

=== Farm.unity ===
   GO Sun                 active=1
   平行光组件数: 1
```

**UI 场景自带一个 `Directional Light`（intensity = 1）。**

加性加载后：
- 农场的 `Sun`（FarmLighting 把它设为 **0.4**）
- UI 的 `Directional Light`（**1.0**）

**两个平行光同时照明 → 场景被照了两遍 → 明显过亮。**

而"直接打开 Farm 场景"时**没有 UI 场景**，所以只有 Sun，亮度正常。

**这一条完整解释了你反复反馈的现象**，而且和 RenderSettings 无关。

### 附带说明：我上一轮的诊断代码有缺陷

我写的是"找第一个平行光并报告"，正好抓到 UI 那个，于是报成 `intensity=1`。
这误导了我自己一轮。**已改成列出全部平行光并标明所属场景。**

## 二、性能：终于算清了

你转储里的 `渲染器 18,932`，我现在能精确对上了：

```
玉米  200 株 × 74 个网格   = 14,800   ← 主体
土壤   36 块 × 111 个网格  ≈  3,996
--------------------------------------
                              18,796  ≈ 18,932 ✅ 对上了
```

### 为什么 Instancing 没能降下来

| | Instancing 能省的 | Instancing **不能**省的 |
|---|---|---|
| draw call 提交 | ✅ 合批（Saved by batching 18,152） | |
| **Unity 每帧遍历的 MeshRenderer 数量** | | ❌ **还是 18,932 个对象要逐个处理** |

**18,932 个 `MeshRenderer` 的 culling + 排序 + 状态管理本身就是主要开销**，
Instancing 只优化了"提交"这一步。

### 而我之前两次"合并"都失败，是因为**粒度错了**

| 做法 | 顶点数 | 结果 |
|---|---|---|
| 合并**整片**玉米（200 株） | ≈ **140 万** | 超 65,535 上限 → 拆几十块 + **几何被复制**（Tris 翻倍）❌ |
| 合并**一株**玉米 | ≈ **7,000** | 每个材质 1 个网格，不拆块、不复制 ✅ |

**正确粒度：按「单个物体」合并，而不是按「整片」合并。**

### 已修

| 改动 | 说明 |
|---|---|
| `MeshCombiner.CombineSingle()` | 新增：合并不拆块（用 32 位索引），几何不复制 |
| `MeshCombiner.CombinePrefab()` | 改用 `CombineSingle` |
| `FarmFieldBuilder.optimizeMeshes` | 默认**开启**（但粒度改成单物体） |
| 删除"对整片 Plants / Soil 再合并一次"的代码 | 那正是导致拆块复制的那一步 |

**预期效果**：

```
玉米  200 株 × 6 材质  = 1,200   （原来 14,800，降 12 倍）
土壤   36 块 × 6 材质  =   216   （原来 3,996）
地形                     ≈   28
房车                     ≈   19
------------------------------
                          约 1,463 个渲染器
```

**从 18,932 降到约 1,463** —— 这才是真正该走的路。

## 三、关于"是不是重来更快"

你说得对，我在修这个问题上花的时间已经远超搭建时间。
**但我不建议推倒重来**，理由是：

| 如果重来 | 现在 |
|---|---|
| 从零搭田块/玉米/巡航/UI 连线 | 这些**都已经能用**（页面能走通、巡航能跑、玉米能随阶段变） |
| 仍会遇到同样的问题：模型碎片化、加性场景的灯光/RenderSettings 冲突 | 这两个**已经定位清楚了**，修法也写进代码了 |
| 再花 3~5 天 | 这一轮改完就能验证 |

**真正该"重来"的不是项目，而是我的排查方法** —— 这一点我认。我犯的错是：

1. **没有第一时间去看"场景里到底有什么"**（应该一开始就 dump 场景/光源/相机）
2. **改了代码没验证是否被执行**（组件不在场景里，白改三轮）
3. **拿到数字没做量纲校验**（18,932 这个数，一除 74 就该发现是玉米网格数）

第 3 条最致命：`18,932 ÷ 74 ≈ 256`，一眼就能看出"这是玉米的网格数"。

**唯一的替代方案**是"把 UI 合并进 Farm 场景，彻底去掉加性加载" ——
那样能一并消除灯光/RenderSettings/相机/音频监听器这一整类问题。
代价是 UI 场景要动（之前误删过一次，风险高）。**如果你倾向这个，我可以做。**

## 六、一句话

- **亮度根因**：UI 场景自带一个 `Directional Light`（强度 1），和农场的 `Sun` 叠加照明。
- **性能根因**：**合并粒度错了** —— 应该按"单个物体"合并（一株玉米 7,000 顶点），
  而不是按"整片"合并（200 株 140 万顶点，必然拆块并复制几何）。
- 修法都已写进代码，**跑一次就能验证**。
