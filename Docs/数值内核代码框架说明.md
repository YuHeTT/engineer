### 关于子目录与命名空间

**分目录不影响命名空间** —— 所有文件都在 `Engineer.Core` 命名空间下，
所以移动文件后**不需要改任何 `using`**。

原因是 `Engineer.Core.asmdef` 里设了 `"rootNamespace": "Engineer.Core"`，
而 C# 的命名空间由源码里的 `namespace` 声明决定，与物理目录无关。
asmdef 会**递归包含**子目录，所以 Core 仍然是一个程序集。

> **注意**：配置层的目录叫 `Settings/` 而不是 `Config/` ——
> 因为工程里已经有一个 `Engineer.Config` **程序集**，
> 用同名目录会让人搞混"改哪个文件"。

### 2.1 基础类型层（`Core/Foundation/`）

#### `SoilMetric.cs` — 土壤指标枚举

定义 9 项土壤指标的编号，**前 5 项动态、后 4 项静态，顺序不可变更**。

```csharp
pH=0, OM=1, N=2, P=3, K=4,      // 动态：参与适宜度与演变
Eh=5, BaseIon=6, As=7, Hg=8     // 静态：第一阶段随机一次后不变
```

配套 `SoilMetrics` 静态类提供：`All` / `Dynamic` / `Static` 数组、`IsDynamic()`、`DisplayName()`（中文名，UI 直接用）。

**为什么用枚举**：配置表里写字符串 `"pH"` 拼错了要到运行时才发现；枚举拼错编译不过。而且数组下标可以 O(1) 取适宜度。

#### `Stage.cs` — 生长阶段枚举

```csharp
S1=0, S2=1, S3=2, S4=3, Done=4
```

对应文档：S1 播种苗期 / S2 营养旺长期 / S3 生殖关键期 / S4 灌浆成熟期。

**`Done` 的存在是有意的**：文档第 5 阶段（收获期）不需要玩家操作，也不参与演算和产量计算。如果把它做成 `Stage.S5`，收益公式 `(S1+S2+S3+S4)/4` 就会混淆。所以收获期在 UI 上是一个界面，在数值上不属于 Stage。

配套 `Stages` 提供 `Count=4`、`All`、`IsPlayable()`、`ToIndex()`、`DisplayName()`、`ShortName()`。
**统一了文档里两套编号**（正文"阶段一/二/三/四/五"与表格"S1/S2/S3/S4"）。

#### `MathX.cs` — 纯 C# 数学工具

因为 `Core` 关闭了 UnityEngine 引用，不能用 `Mathf`。提供 `Clamp` / `Clamp01` / `Min` / `Max`（含 int 重载）/ `Lerp` / `InverseLerp` / `Remap` / `InRange` / `InRangeHalfOpen` / `ApproxEqual`。

**存在的意义**：让"不依赖 UnityEngine"这条约束在实现层面自洽，而不是靠自觉。

### 2.2 适宜度计算层

#### `SuitabilityCurve.cs` — ★ 适宜度曲线

**整个数值内核最核心的一个类。** 把"土壤指标的实际数值"换成"对玉米的适宜程度"。

文档给了 5 张适宜度函数表（fPH / fOM / fN / fP / fK），但**分段结构完全相同**，都是五段：

```
    适宜度
       1.0 |          ______________
           |         /              \
           |        /                \
       0.2 |_______/                  \_______
           +-------|-------|-------|-------→ 指标数值
                  B0      B1      B2      B3
           <B0:保底  [B0,B1)升  [B1,B2]平  (B2,B3]降  >B3:保底
```

所以只写一个 `Evaluate(value)`，五个指标的差别只是 B0..B3 的取值。这样"加新指标"或"改区间"都只改配置。

**边界语义（实现时已严格对齐文档）**：左侧半开 `[B0, B1)`、平台闭区间 `[B1, B2]`、右侧半开 `(B2, B3]`。

还提供 `InverseOnRising()`（反推：要多少指标值才能达到某适宜度）、`GetOptimalRange()`（给 UI 提示目标区间）、`Validate()`（挡住"边界写反"这类错误）。

#### `SuitabilityResult.cs` — 五个适宜度

承载某一阶段的 `fpH / fOM / fN / fP / fK`。

关键方法：
- `StageFertility()` → `fPH × fOM × fN × fP × fK`（文档 TABLE 14 行 6 的阶段肥力系数）
- `Min()` / `All()` / `Any()` / `Count()` → 给推荐方案表的条件判定用
- **`static From(SoilState, SimConfig)`** → **唯一的计算入口**，别在别处手写分段函数

#### `SoilState.cs` — 9 项土壤数值

9 个具名字段（`pH` / `OM` / … / `Hg`），加一个按 `SoilMetric` 索引的 indexer。

**为什么不用 `float[9]`**：具名字段在代码里可读（`state.pH` 比 `state[0]` 清楚）；字段名就是 CSV 列名，导入器能直接对应；取适宜度时走 indexer 兼顾性能。

`Clone()` 用于跨阶段传递，避免引用共享。

#### `SoilGenerator.cs` — 初始土壤生成

按文档要求合成初始土壤：**动态五项取自用户输入，静态四项按 TABLE 2 随机**。

- `Generate(userInput, config, rng)` — 主入口
- `MakeMidpointInput(config)` — 取区间中值（测试与默认值用）
- `MakeAtRatio(config, t)` — `t=0` 取下界、`t=1` 取上界（批量验证"区间四角"用）
- `ClampToInputRange()` — 挡住非法输入

**`System.Random` 而非 `UnityEngine.Random`**，所以支持传 seed：策划复现问题、批量验证跑几千组、将来做存档重放都靠它。

### 2.3 推荐方案层

#### `PlanCondition.cs` — 判定条件

把文档 TABLE 13"适宜度判定条件"列变成可求值的数据结构。文档的条件只有 5 种形态，所以只有 5 个枚举值：

| 类型 | 对应文档写法 |
|---|---|
| `Below` | `fN＜0.6（其次 fP）` |
| `AnyBelow` | `fN 或 fP 或 fK＜0.6` |
| `AnyInRange` | `任意项 0.6~0.8` |
| `AllAbove` | `全部≥0.8` |
| `AllAboveAndCount` | `全部≥0.6 且≥3 项≥0.8` |

**`Scope` 字段**限定参与判定的指标集合，为空表示全部五个动态指标。
**边界语义全表统一**：`＜0.6` 用严格小于，`≥0.8` 用大于等于。
`Describe()` 生成可读描述，日志与调试窗口直接用。

#### `PlanRule.cs` — 推荐方案表的一行

把"条件 + 结果"绑成一条规则。字段：`Stage` / `Priority` / `Condition` / `Label` / `Physiology` / `Amounts` / `BaseIrrigation` / `IsFallback`。

**`Priority` 是必须的**：文档的表不是互斥条件表，而是有先后顺序的分支（S1 前两行、S3 前两行都可能同时成立），必须靠优先级决定用哪个。

#### `PlanTable.cs` — ★ 有序匹配 + 兜底

给定"阶段 + 五个适宜度"，从规则表里挑出唯一一条。

**三级匹配 —— 因为文档规则表并不完备**（这是实测发现的）：

```
1) 按 Priority 找精确匹配
2) 没有精确匹配时，用标记为 IsFallback 的规则（"缺什么补什么"那条）
3) 连兜底都没有，才退回最高优先级规则，并置 LastMatchUsedFallback = true
```

**文档规则的真实空洞**（阈值采样 25 万组 × 4 阶段实测）：

| 阶段 | 空洞组数 | 典型情况 |
|---|---|---|
| S1 | 16384 | 全部 = 0.6（行1要 `<0.6` 不成立、行2要 `≥3项≥0.8` 也不成立） |
| S2 | 81920 | fN=0.8 但 fP/fK 很低（S2 只判定 fN，缺磷却没有对应建议） |
| S3 | 3072 | fPH/fOM 很低但 N/P/K 都 ≥0.8 |
| S4 | 81920 | fK=0.8 但其他很低（S4 只判定 fK，同理） |

**没有兜底会怎样**：Match 返回 null，UI 拿到空建议就崩。有了兜底，"缺磷就补氮磷"这种合理降级能自动生效。

另外提供 `RulesOf(stage)`（UI 展示完整方案表）和 `CheckCoverage()`（覆盖性自检，支持自定义采样点）。

#### `RecommendedPlan.cs` — 推荐方案 + 复合肥折算

系统给出的方案。含 `FertilizerAmounts`（有机肥 / N / P / K / **复合肥**）。

**复合肥折算是这里的核心职责**。文档 S3 有一行"复合肥 14"，但演算公式只认氮磷钾有机肥四项，必须折算。已确认 **1:1:1**：

```csharp
ToApplication(config)   // 14 × (1/3) = 4.667 分别加到 N/P/K
```

折算比例走 `SimConfig.CompoundRatio`，策划改比例不用动代码。

### 2.4 演算层

#### `FertilizerApplication.cs` — 玩家实际投入

对应文档的水肥输入面板五项：`Irrigation` / `Organic` / `N` / `P` / `K`。

**故意不含 `Compound` 字段** —— 输入面板上本来就没有这一项。折算发生在推荐方案侧，两种来源（玩家输入、系统建议）最终统一成这同一个结构，演算只认它。

#### `SoilAdvance.cs` — ★ 阶段演算

数值内核里**唯一的"演化"逻辑**，决定了玩家的操作能不能被看见。

```
有效水比例 = min(实际灌溉 ÷ 建议灌溉, 1)
超灌比例   = max(实际 − 建议, 0) ÷ 建议

新pH = 当前pH + (6.25 − 当前pH) × 有机肥/80 × 0.1 × 有效水比 − 0.15 × 氮肥/12 × 有效水比
新OM = 当前 + 7.5 × 有机肥/80 × 有效水比 − 1.5 − 1.5 × 超灌比
新N  = 当前 + 20 × 氮肥/12 × 有效水比 − 本阶段氮消耗 − 4 × 超灌比
新P  = 当前 + 7.5 × 磷肥/5 × 有效水比 − 本阶段磷消耗 − 1.5 × 超灌比
新K  = 当前 + 50 × 钾肥/10 × 有效水比 − 本阶段钾消耗 − 10 × 超灌比
```

**三个必须知道的行为**（都已在文档记录、代码注释里也标了）：

1. **有效水比例封顶为 1** → 灌够了之后多灌不再加分，但超灌比例还在涨，即**多灌只会有惩罚**。
2. **pH 两项配比相反**：有机肥项 `0.1` 弱于氮肥项 `0.15`，所以**照抄推荐方案 pH 会净下降**（实测起点 6.90 → 终点 6.81）。策划已知，v1 保留原值。
3. **pH 公式里没有超灌项** → 灌多灌少对 pH 完全一样。

`SafeDiv()` 做除零保护，避免配置里参考量写 0 时产生 NaN 污染整条链路。

#### `StageResult.cs` — 单阶段结果快照

一次阶段结算的全部信息，供 UI 显示与调试导出。

**为什么需要它**：UI 在"开始分析"界面要同时显示本阶段土壤、五个适宜度、系统建议、玩家实际填的值、算完后的下一阶段。如果结算方法只返回一个 `SoilState`，UI 就得自己重算一遍，容易不一致。所以让 `Commit()` 一次性返回全部。

辅助方法：`EffectiveWaterRatio()` / `OverWaterRatio()` / `DeviationFromRecommendation()`（玩家偏差，UI 提示用）。

### 2.5 产出层

#### `GrowthLevel.cs` — 长势三档

```csharp
Good(好) / Normal(正常) / Bad(差)
```

判定按**已确认的修订**：`全部 > 0.6` → 好；`全部 < 0.6` → 差；**其余一律正常**。

**注意用的是严格不等号**：`f == 0.6` 既不算好也不算差 → 正常。五项都恰好 0.6 时也是正常，这是有意为之。

`GrowthLevels.AssetSuffix()` 给出资源命名后缀约定（`好` / `正常` / `差`），对应美术已有的 `玉米_幼苗_好` / `玉米_成长_正常` / `玉米_成熟_差` 命名。

#### `YieldModel.cs` — 产量模型【全工程唯一的公式实现】

```
Ffert,stage = fPH × fOM × fN × fP × fK
Ffert       = (S1 + S2 + S3 + S4) / 4
Fwater      = (α1·Fw,s1 + α2·Fw,s2 + α3·Fw,s3 + α4·Fw,s4) / Σα
Sstatic     = 1
Y           = Ymax,geo × Ffert × Fwater × Sstatic
```

**公式只写在这里**：调用链固定为 `Simulation.Revenue()` → `RevenueReport.Create()` → `YieldModel.Compute()`。
`Compute()` 一次把 `Ffert` / `Fwater` / `Sstatic` / `Y` 全算出来（返回 `YieldBreakdown`），调用方只读结果 ——
这样"界面显示的中间量"和"算 Y 用的中间量"物理上不可能是两个数。

**`Fwater` 和 `Sstatic` 保留成参数而不是写常量 1** —— 文档说"因系统总给最优灌溉，Fwater=1"，
但后续要接"水分胁迫"时不用改函数签名。`Alpha[]` 权重也已预留；
`SimplifiedWaterFactors()`（返回全 1）是 **v1 水分因子的唯一出处**，
将来接了 Fw,s 公式只改它或 `Simulation._stageWaterFactors` —— 合成 `Fwater`、报告、界面都不用动。

> **一处文档不一致（已按意图实现）**：文档 [246] 写 `÷4`，但 [247] 的 α = 0.2/0.2/0.4/0.2 **和为 1**；
> 照字面代入 [248] 的 `Fw,s = 1` 会得到 `(0.2+0.2+0.4+0.2)/4 = 0.25`，与 [249] 的 `Fwater = 1` 矛盾。
> 实现按 **Σα 归一化**（α 和为 1 时等价于 `Σα_i·Fw,s_i`），全 1 时 `Fwater` 恰好 = 1。
> 若策划确认要按字面 ÷4，只需改 `WaterFactor()` 的最后一行。

#### `RevenueReport.cs` — 收益报告

最终界面（文档"收益计算"那屏）的数据源，**只允许由 `RevenueReport.Create()` 生成**（唯一组装入口，
内部调 `YieldModel.Compute()`）。含四阶段肥力系数、阶段水分因子、平均肥力、`Y`、`YmaxGeo`、最终土壤、土地面积，以及：

- `AchievementRate` — 产量占理论上限的百分比（界面上的"达成率"）
- `TotalYield` — 总产量 = 单位面积产量 × 面积
- `CommittedCount` / `IsPartial` — 已结算了几个阶段；四阶段没跑完时报告是**中间态**，
  `Ffert` **只对已结算阶段求平均**（不会把未结算阶段按 0 摊进去），界面据此加一行提示
- `WaterNote` — 水分那一行的说明文案（v1 说"总给最优灌溉"，接了 Fw,s 后自动改成列各阶段值），UI 不许写死
- **`PricePerKg` / `TotalCost` / `GrossIncome` / `NetIncome` 是预留的经济层字段**

**文档在这里有一处不一致**：说"输出 Y 作为最终收益"，但 Y 的单位是 kg/亩（产量），不是钱；界面叫"收益计算"却没有价格和成本。策划已确认成本后续再加，所以这里同时保留产量与经济层两套字段。

### 2.6 配置层

#### `SimConfigParts.cs` — 配置的组成部分

| 类 | 对应文档 | 作用 |
|---|---|---|
| `StaticMetricRange` | TABLE 2 | 静态指标随机范围，`Sample(rng)` 取值 |
| `StageConsume` | TABLE 18 | 各阶段氮磷钾消耗量 |
| `AdvanceCoef` | "补充"节 | 全部演算系数，**pH 两个系数带详细的已知问题注释** |
| `TerrainDef` | TABLE 0 | 四套地形（ID / 名称 / 介绍 / 模型 / v1 是否可玩） |
| `CropDef` | TABLE 1 | 四种作物，含 `Curves` 引用（多作物时各挂一套） |
| `YieldConfig` | 收益段 | `YmaxGeo`（占位 1000）/ 水分权重 / `SStatic` |

#### `SimConfig.cs` — ★ 数值总配置

**所有数值设定的唯一来源，绝不硬编码常数。**

内容：`Curves[5]` + `DynamicInputRanges[5]` + `StaticRanges[4]` + `Terrains` + `Crops` + `PlanRules[11]` + `StageConsumes[4]` + `Advance` + `CompoundRatio` + `Growth` + `Yield`。

核心是 **`CreateDefault()`**：唯一一处集中出现字面数值的地方，按文档填好全部数值。11 条推荐规则在 `BuildDefaultPlanRules()` 里，带优先级、带 `IsFallback` 标记、带文档原文的文案。

辅助方法：
- `CurveOf(metric)` / `RangeOf(metric)` / `ConsumeOf(stage)` — 安全取值
- **`Validate(errors, warnings)`** — 区分**错误**（配置坏了，必须修）与**警告**（文档规则表不完备，已由兜底接管）

#### `Simulation.cs` — ★ 总入口状态机

对外只暴露 5 个方法，UI 层只跟它打交道。

**设计要点：能单步推进，而不是一次跑完。** 因为每个阶段之间都要插入玩家操作：

```csharp
var sim = new Simulation(cfg);
sim.Initialize(玩家输入的土壤);          // 选定地形与基础数据后

while (!sim.IsFinished)
{
    var fit = sim.Evaluate();            // 当前适宜度
    var rec = sim.Recommend();           // 当前建议
    // ...UI 显示，等玩家填水肥...
    var result = sim.Commit(玩家投入);    // 结算并推进
}

var report = sim.Revenue();              // 收益报告
```

`Commit()` 内部的**顺序很重要**：先用旧土壤算适宜度（得本阶段成绩），再演算得新土壤。顺序反了会变成"本阶段成绩受本阶段操作影响"，与文档不符。

**只有两处能改土壤**：`Initialize` 和 `Commit`。对外只暴露只读的 `CurrentSoil`，避免 UI 层误改。

还提供 `GetHistory(stage)` / `History`（回看与导出）、`DumpHistory()`（一行行文本，日志与策划评审用）。

### `BatchValidationWindow.cs` — 数值批量验证

### `RevenueChainCheck.cs` — 收益链路自检

菜单：**Engineer / 收益链路自检**

命令行（不开界面也能跑）：

```
Unity.exe -batchmode -quit -nographics -projectPath <工程> \
          -executeMethod Engineer.Editor.RevenueChainCheck.Run -logFile -
```

把"收益公式全工程只有一份、各屏拿到的数一致"变成一条能随时重跑的回归检查（当前 **18 项全绿**）：

| 组 | 检查什么 |
|---|---|
| 1. 完整四阶段 | 报告里的 `Ffert` / `Y` 与独立重算一致；`Fwater = 1`；`Y = Ymax × Ffert × Fwater × Sstatic`；达成率、总产量 |
| 2. 只结算 2 阶段 | `IsPartial = true`；`Ffert` 只对已结算阶段求平均（退回"未结算按 0 摊"立刻判失败） |
| 3. 水分因子与 α 权重 | `Fw,s` 全 1 ⇒ `Fwater = 1`；α 加权（S3 权重 0.4、`Fw,s3` 减半）⇒ `0.8`；报告能自己说明水分是否简化 |
| 4. 报告快照 | 继续推进模拟不会改写旧报告；报告持有的是数组/土壤的副本 |

自检内部**自己实现一遍平均**，特意不调 `YieldModel`，避免"用同一段代码验证它自己"。

## 五、数据流全景

```
                           SimConfig（配置）
                                 │
    ┌────────────────────────────┼────────────────────────────┐
    │                            │                            │
    ▼                            ▼                            ▼
SuitabilityCurve            PlanRule[]                  AdvanceCoef
（五条曲线）                 （11 条规则）                StageConsume[]
    │                            │                            │
    │                            ▼                            │
    │                       PlanTable ────优先匹配+兜底        │
    │                            │                            │
    ▼                            ▼                            │
  SoilState ──From()──> SuitabilityResult ──Match()──> RecommendedPlan
    │                       │       │                       │
    │                       │       └──GrowthRule──> GrowthLevel（贴图）
    │                       │                               │
    │                  StageFertility()                     │
    │                       │                               │
    │                       ▼                               ▼
    │              YieldModel（四阶段平均）         SoilAdvance（演算）
    │                       │                               │
    │                       ▼                               ▼
    └──────────────> RevenueReport                    SoilState（下一阶段）
                                                            │
                                                            └──> 回到 SoilState，循环
```

**关键点**：
- `SuitabilityResult.From()` 是适宜度的**唯一计算入口**
- `SoilAdvance.Advance()` 是演化的**唯一实现**
- `RevenueReport.Create()` 是收益报告的**唯一组装入口**，公式只在 `YieldModel` 里
- `PlanTable.Match()` 保证**永不返回 null**
- 所有数值都来自 `SimConfig`，改数值不改代码

## 六、怎么用（最小示例）

```csharp
using Engineer.Core;
using Engineer.Config;

// 1. 拿配置（两种方式）
var cfg = SimConfig.CreateDefault();              // 纯代码
// 或在 Inspector 里挂 SimConfigAsset，然后：
// var cfg = myAsset.BuildSimConfig();

// 2. 建模拟并初始化
var sim = new Simulation(cfg);
var input = SoilGenerator.MakeMidpointInput(cfg);  // 或用玩家输入
sim.Initialize(input, new System.Random(12345));   // seed 可复现

// 3. 逐阶段推进
while (!sim.IsFinished)
{
    var fit = sim.Evaluate();          // 五个适宜度
    var rec = sim.Recommend();         // 推荐方案
    var grow = sim.CurrentGrowth();    // 长势（切贴图）

    // UI 显示 fit / rec / grow，等玩家填水肥
    var applied = new FertilizerApplication(
        rec.BaseIrrigation,            // 灌溉
        rec.Amounts.Organic,           // 有机肥
        rec.Amounts.N, rec.Amounts.P, rec.Amounts.K);

    var result = sim.Commit(applied);  // 结算
}

// 4. 收益
var report = sim.Revenue(area: 100f);  // 100 亩
UnityEngine.Debug.Log(report.ToString());
```

## 八、新增发现：文档规则表不完备

这是本轮实现**新发现**的问题，之前用 Python 脚本没测出来（采样点没落在阈值上）。

**文档 TABLE 13 的规则之间存在真实空洞**，实测数据：

| 阶段 | 空洞组数 | 为什么 |
|---|---|---|
| S1 | 16384 | 行1 要"任意项 `<0.6`"、行2 要"全部 `≥0.6` 且 `≥3项≥0.8`"，两者之间有夹缝 |
| S2 | 81920 | **只判定 fN**。fN 很高但 fP/fK 很低时，三条规则都不成立 |
| S3 | 3072 | 行1 只看 N/P/K，行3 要"全部 ≥0.8"。pH/OM 很低但 N/P/K 都高时无匹配 |
| S4 | 81920 | **只判定 fK**，问题同 S2 |

**当前处理**：`PlanTable` 三级匹配，用标记了 `IsFallback` 的"缺什么补什么"规则兜住，**保证 Match 永不返回 null**。代码不会崩，但**给出的建议不是文档定义的**。

**建议反馈给策划**：需要为 S2/S4 补上"其他指标也偏低"的分支（例如 S2 增加"fP < 0.6"或"fK < 0.6"的规则），否则大量输入会走到未经定义的建议上。
