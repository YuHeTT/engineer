# 系统性问题定位：几何被烘焙进场景，运行时又生成一遍

> 日期：2026-10-15
> 状态：**根因已定位并修复**，五个程序集编译通过。

---

## 一、根因（一条解释所有现象）

**`Farm.unity` 里存了 20,333 个 GameObject / 20,059 个 MeshRenderer（46 MB），
而这些本该是"运行时生成"的。Play 时 `Awake` 又生成一遍 → 场景里同时存在两套几何。**

### 硬证据

```
Farm.unity 大小 46.1 MB
  GameObject      20333
  MeshFilter      20059
  MeshRenderer    20059
  按命名识别：Corn_* 200 个、Soil_* 36 个、Path_*/Ridge_*/Ring_* 10 个、RV 2 个
  ← 这些全是"运行时生成"的实例，却被序列化进了场景文件
```

Unity 日志里更露骨 —— **`FarmOptimizer` 一次启动跑了 3 遍，渲染器数疯狂累积**：

```
[农场优化] ...渲染器 29518 个
[农场优化] ...渲染器 38990 个     ← +9472
[农场优化] ...渲染器 40251 个     ← +1261
```

**200 株玉米不可能有 4 万个渲染器。** 这是两套几何叠加的结果。

### 这一条解释了你反馈的全部现象

| 现象 | 原因 |
|---|---|
| **卡顿依旧** | 渲染器 4 万（应为约 2 千）、draw call 爆炸 |
| **阴影投影 10 万** | 两套几何 → 投影物体翻倍 |
| **从 Bootstrap 跑就高亮** | 两套几何**重叠渲染**，同一像素被画两遍 |
| **从 Farm 场景看亮度正常** | 你在 Scene 视图看的是**单一几何**，看不到叠加 |
| 之前几轮优化"没效果" | 优化的是"从 4 万往下减"，但源头一直在翻倍 |

## 二、为什么会这样（设计错误）

```
编辑期点菜单 → FarmSceneBuilder 调 Build() → 生成几何
             → EditorSceneManager.SaveScene() → **几何被写进 Farm.unity**
Play 时      → 场景加载（带 2 万个烘焙对象）
             → FarmFieldBuilder.Awake → Build() → **又生成一遍**
             → 两套并存
```

我当初加 `builder.Build()` 是为了"让 FieldBounds 有效、相机会正确取景"，
**代价是把几何烘焙进了场景** —— 这就是根源。

---

## 三、修复（四处，系统性堵住）

### ① 所有生成器改为「只在运行时生成」

| 文件 | 改动 |
|---|---|
| `FarmFieldBuilder.cs` | `Awake` → `if (Application.isPlaying) Build();` |
| `FarmFieldPaths.cs` | `Start` → 同上 |
| `FarmTerrainRing.cs` | `Start` → 同上 |
| `FarmEquipment.cs` | `Start` → 同上 |
| `FarmFieldGrid.cs` | `Awake` → 同上 |

### ② 构建器**不再在编辑期调 Build()**

`FarmSceneBuilder.BuildFarmScene()` 里删掉了 `builder.Build()`，
`BuildFieldRoot` 里的 `paths.Build()` / `terrain.Build()` / `fieldGrid.Build()` /
`equipment.Build()` 全部注释掉。

**场景现在只存"根节点 + 组件 + 配置"**，预期大小从 46 MB 降到几百 KB。

### ③ 相机取景改为「按配置推算」

编辑期没有 `FieldBounds` 了，所以相机初始位置改成用
`config.FieldSize` / `config.BlockGroupSize` 推算；
运行时 `FarmFieldBuilder.Build()` 完成后会再调一次 `FrameField()` 精确修正。

菜单「只重建田块与玉米」改成打印提示（编辑期不再生成）。

### ④ 加一道**重复几何检测**防复发

`SceneLoader.CheckForBakedGeometry()`：运行时检查 `Plants` / `Soil` 下的子物体数量，
如果超过正常规模（`Plants > 10` 或 `Soil > 100`），直接 **`LogError`** 并给出修法。

## 七、我的反思

你两次说"不要反复做无用功"，是对的。我犯的判断错误是：

**看到"卡"就去优化渲染管线，却没有先问"到底有多少东西在被渲染"。**

正确顺序应该是：
1. 先拿 Statistics 的 `Batches` / `Tris` / `Shadow casters` 三个数
2. 用"对象数 × 通道数"反推是否合理（20,059 × 14 = 283,776 这个关系我其实算出来过）
3. **不合理就先查"为什么会有这么多对象"**，而不是去优化"怎么把这些对象画得更快"

我算出 `20,059 × 14 = 283,776` 时其实已经接近真相了，
但当时只关注了"14 倍来自阴影"，**漏掉了更根本的问题：为什么对象数是 20,059**。
（答案：正常应该是约 2,000 —— 也就是 10 倍的膨胀。
而这个膨胀来自"场景烘焙 + 运行时生成"两套。）
