# 《Unity界面.docx》方案分析（第一版 Demo）

> 分析对象：仓库根目录 `Unity界面.docx`（策划产出，第一版，部分功能未完成）
> 工程现状：Unity 2022.3.62f2c1；`Assets/Scripts` 为空，`SampleScene` 为空场景，
> 现有一份可用的房车模型（精细可开合 v2）、四套地形 glb、玉米与土壤模型包、画风参考图。
> 结论：**文档是完整的设计意图，工程是零实现。后续工作基本等于"从这份文档落地一整套系统"。**

---

## 一、方案在做什么（一句话）

一个**单机、线性、五阶段**的"数字农田管理决策演示"：
选地形 → 设土壤本底 → 选作物 → 每阶段「机器人巡航采样 → 系统算适宜度 → 给水肥建议 → 玩家填水肥 → 推进下一阶段」→ 第五阶段结算产量 Y。
定位是**可交互、可解释的科普/竞赛演示**，不是有胜负和失败态的"游戏"。

## 三、被完整定义的部分（可以立刻写代码）

1. **土壤指标体系（9 项）**
   - 动态 5 项：酸衡值 pH、腐殖丰度 OM、速效氮元 N、磷活度 P、钾储量 K
   - 静态 4 项：氧还势 Eh(400~550)、土骨离子(7~16)、毒砷潜势(5~15)、汞积量(0.03~0.12)，第一阶段随机生成后全程不变

2. **五个适宜度分段函数（fPH / fOM / fN / fP / fK）**
   全部是"下限保底 0.2 → 线性上升 → 最优区间 1.0 → 线性下降 → 上限保底 0.2"的同构结构，参数齐全：

   | 因子 | 保底 | 上升段 | 最优段 | 下降段 | 保底 |
   |---|---|---|---|---|---|
   | pH | <4.5 → 0.2 | 4.5–5.5 | 5.5–7.0 | 7.0–8.5 | >8.5 → 0.2 |
   | OM | <10 → 0.2 | 10–20 | 20–35 | 35–50 | >50 → 0.2 |
   | N | <20 → 0.2 | 20–70 | 70–110 | 110–150 | >150 → 0.2 |
   | P | <2 → 0.2 | 2–10 | 10–25 | 25–40 | >40 → 0.2 |
   | K | <40 → 0.2 | 40–100 | 100–200 | 200–280 | >280 → 0.2 |

3. **推荐水肥方案总表（S1–S4，共 11 条规则）** —— 判定条件、肥料类型、单亩施肥量、单亩基准灌溉、生理说明齐全。这张表是整个玩法的骨架。

4. **灌浆前的指标演算（唯一的真·动态机制）**
   - 有效水比例 = min(实际灌溉 ÷ 建议灌溉, 1)
   - 超灌比例 = max(实际 − 建议, 0) ÷ 建议
   - 下一阶段 pH / OM / N / P / K 各有明确公式（pH 向 6.25 靠拢、OM +7.5 系数、N +20、P +7.5、K +50，各带消耗与超灌惩罚）

5. **阶段消耗量表**：S1 氮 3.33/磷 2.25；S2 氮 10/磷 3.75；S3 氮 6.67/磷 3/钾 25；S4 钾 22.5

6. **产量模型**：Ffert,stage = fPH×fOM×fN×fP×fK；Ffert = (S1+S2+S3+S4)/4；Fwater 恒为 1；Sstatic = 1；Y = Ymax,geo × Ffert × Fwater × Sstatic

7. **长势分级**：好 / 正常 / 差 三档贴图；S1 只见土地，S5 与 S4 共用贴图

8. **采集机制**：机器人周身球形碰撞体积扫过玉米田网格，覆盖面积递增 → 探测数据按顺序逐条显示 → 全部覆盖后点「更新数据」覆盖原数据

## 四、方案的优点

1. **流程闭环、线性无死路。** 12 屏顺序严丝合缝，有「返回上一步」，有「开始新的模拟」，演示时不会卡住。
2. **数据模型是"可计算"的，不是纯文案。** 分段函数、系数表、演算公式、产量公式都给了具体数字——这一点比大多数学生项目的策划案强很多，直接就能写成 `ScriptableObject` 或 JSON 配置。
3. **"探测数据 / 原数据"双栏 + 更新机制，是这套方案最有游戏感的巧思。** 它把"我看到的土壤数据可能不准"变成了玩家可感知的一步操作，天然解释了为什么要跑机器人。
4. **UI 结构高度统一**（左上提示 / 右上阶段 / 底部数据+操作），四屏农场界面共用同一 HUD 骨架，实现成本低、视觉一致。
5. **美术资源已经对得上。** 房车（含开合动画）、四套地形 glb、玉米与土壤模型包都已入库，第 7–12 屏的第三人称农场是有素材支撑的，不是空想。
6. **工程侧的基础设施到位。** Force Text 序列化、`.gitattributes` 智能合并、README 讲清楚了 `.meta`/`Library`/LFS 的规矩，团队协作不会踩低级坑；仓库现有素材约 155MB，暂无 LFS 压力。
7. **提示文案写得具体。** "请通过机器人探测，设置水肥来收集所有数据"这类话直接就能当 UI 文本用，省掉一轮文案往返。

## 五、问题与风险

### A. 数值设计（最需要先解决的一类）

| 编号 | 问题 | 说明与建议 |
|---|---|---|
| A1 | **按建议操作 = 土壤几乎零变化** | S1 氮：+20×4/12 = 6.67，消耗 3.33 → +3.33；磷 +7.5×3/5 = 4.5，消耗 2.25 → +2.25；S2 氮 +10 消耗 10 = 0，磷 +4.5 消耗 3.75 = +0.75。**严格照抄推荐，五阶段指标几乎不动，模拟失去"演化"感。** 建议给每阶段加自然项（淋溶、矿化、盐分累积、降雨），或让消耗略大于推荐施肥，制造趋势与压力 |
| A2 | **超灌只惩罚氮磷钾和 OM，不惩罚 pH** | pH 公式里只有"有效水比例"没有"超灌比例"。而且有效水比例被封顶为 1，所以**灌多灌少对 pH 完全一样**。建议 pH 也吃超灌项（淋溶/盐渍化） |
| A3 | **百分比写法与指数写法混用，量级不明** | pH 公式写 `0.1`、氮写 `0.15`，其他地方一律 `×0.8` 这种系数。这些 0.1/0.15 到底是"百分点"还是"乘数"必须写死，否则两个人实现出两套数值 |
| A4 | **"复合肥 14"无法参与演算** | S3 有一条推荐是"复合肥 14 kg/亩"，但下一阶段公式只认氮肥/磷肥/钾肥/有机肥四项。复合肥→氮磷钾的折算系数缺失。建议要么改名并给出拆分比（如 15-15-15），要么删掉这条 |
| A5 | **Ymax,geo 未定义** | 产量公式里最关键的常数完全没有数值。而且"输出 Y 作为最终收益"里的 Y 是**单位面积产量（kg/亩）**，不是收益。界面叫"收益计算"却没有价格、成本、产值——竞赛若要求体现"收益"，这里必须补经济层 |
| A6 | **四个静态指标完全悬空** | 氧还势、土骨离子、毒砷潜势、汞积量只在界面上显示，不进入任何公式、不影响任何结果。要么接入（如毒砷/汞超标直接压低 fPH 或设产量上限），要么明确它们只是"展示数据" |
| A7 | **长势三分档存在判定死区** | "好=全部>0.6 / 正常=3 项>0.6 / 差=全部<0.6"，那么"只有 2 项 >0.6"落在哪一档？没有定义。另外"所有适宜度<0.6"应为"≤"，否则 0.6 又是空洞 |
| A8 | **fPH 的描述与公式自相矛盾** | 正文写"完全不适宜可趋近于零"，但表格下限是保底 0.2。需二选一 |
| A9 | **乘法模型过于敏感，且"最短板"被淹没** | 五个因子连乘，单因子 0.2、其余 1.0 时 Ffert = 0.2；但推荐表只按"任意项<0.6"给方案，一个 0.2 和一个 0.55 得到同样的建议。建议考虑几何平均或加权，或让推荐表区分严重程度 |
| A10 | **量纲与单位未定义** | pH 无量纲；OM/N/P/K 是 mg/kg 还是 g/kg 还是 %？只说"速效氮元（70~130）"无法校验也无法做真实感校准。土地面积（亩）如何影响施肥总量（单亩量×亩数）也没写 |
| A11 | **作物/地形的差异化机制缺失** | 文档明说"只能选平川台""只能选玉米"。另外三种地形和三种作物**没有任何数值参数**——如果地形只影响一段介绍文字和模型外观，那四个卡片就是装饰。若要扩展，地形至少应影响保水/排水（即超灌惩罚权重）或初始 pH/OM |

### B. 流程与状态

| 编号 | 问题 |
|---|---|
| B1 | **阶段数不自洽**：正文说"玉米四阶段生长模型"，实际是五阶段；`S1/S2/S3/S4` 与"阶段一/二/三/四/五"两套编号并存；推荐表里 S1 占了 2 行（且判定条件互相重叠、不互斥），阶段与推荐行不是一对一 |
| B2 | **第五阶段的行为未定义**：收获期没有基准灌溉量，也要"机器人检测"，但检测出来的数据没人用（收益只看 S1–S4）。要么删掉 S5 的巡航，要么让 S5 的数据影响品质/等级 |
| B3 | **数据源三层关系（原数据 / 探测数据 / 当前真实值）没写清楚**：更新数据后是"覆盖"，那上一阶段已消耗的真实值算哪一层？探测值是否带噪声、噪声随覆盖面积如何衰减？这是实现时必吵的地方 |
| B4 | **第 7 屏（S1）也画了"机器人检测"按钮，但 S1 的数据是用户自己输入的**，探测出来和自己填的一样，没有信息增益。是漏画还是有意？ |
| B5 | **巡航完成判据含糊**："球形轨迹面积覆盖整个玉米田"——是严格 100% 覆盖，还是达到阈值？手动模式下玩家绕不完整块田会不会卡死？自动巡航的 S 形路点是否要按未覆盖区域动态生成？ |
| B6 | **无失败态、无资源约束** | 水肥量没有成本、没有上限，超出建议值除了"超灌惩罚"外无代价。加上推荐表直接给出最优解，**玩家最优策略就是"照抄建议"**，"用户可自主调整管理方案"这个卖点在数值上不成立 |

### C. 表述与术语（评审会看的细节）

- **界面命名待审**：文档标题写"Unity界面"，但产出物是设计说明书，建议改名。
- **指标术语建议统一为农业规范名**：酸衡值→土壤 pH；速效氮元→速效氮（碱解氮）；土骨离子→土壤盐基离子；氧还势→氧化还原电位 Eh；毒砷潜势→砷有效性/砷污染潜势；汞积量→汞累积量。现在这套自造词会让农业背景的评委第一眼打问号。
- **表 0 错别字**："坡度超过高" → "坡度过大/坡度较陡"。
- **与项目简介不一致**：简介写"无人机和地面巡检机器人采集数据"，UI 里只有地面机器人（房车）；房车在画面上是"停着"的，机器人本体是谁也需明确。

## 六、需要向策划确认的问题（按优先级）

1. `Ymax,geo` 取多少？"收益"是产量还是产值（元/亩）？若要用钱，玉米单价与肥料/灌溉成本各是多少？
2. 按建议操作时指标几乎不变（A1）——是有意让玩家"稳"，还是希望出现演化趋势和翻车可能？
3. 四个静态指标（Eh/盐基离子/砷/汞）到底参不参与计算？
4. "复合肥 14"如何折算成氮磷钾？
5. pH 的 0.1 / 0.15 是百分点还是乘数？
6. 长势三分档碰到"恰好 2 项 >0.6"怎么办？是否改成 N 档贴图 / 参数化（缩放、颜色、密度）？
7. S5 是否还需要巡航？S5 数据有无用途？
8. 探测数据是否带噪声？噪声随覆盖面积如何收敛？
9. OM/N/P/K 的单位是什么（mg/kg？g/kg？%）？土地面积如何参与计算（单亩量×亩数）？
10. 地形与作物的差异化是否在本版范围内？若在，参数谁给？
11. 手动巡航的玉米田是网格地块还是连续地形？覆盖判定用网格计数吗？
12. 输入用旧 Input Manager 还是新 Input System？（文档要求 WASD + 第三人称）

## 七、后续工作建议

### 落地顺序（建议）

1. **先做数值内核，不做 UI。** 把 5 个分段函数、推荐表、指标演算、产量公式写成一个纯 C# 的 `SoilModel` 类库（无 MonoBehaviour 依赖），配单元测试。给一个控制台/编辑器窗口就能跑完五阶段，先把数值跑通再谈表现。
   - 好处：数值问题（A1–A11）在这一步就会全部暴露出来，成本远低于做完 UI 再改。
2. **数据配置化。** 推荐表、分段函数参数、阶段消耗全部做成 `ScriptableObject` 或 JSON 表，让策划能自己调，不用每次改代码。文档里这些表结构已经非常适合直接搬。
3. **再搭 UI 骨架。** 抽一套 HUD 预制体（左上提示 / 右上阶段 / 底部数据面板）+ 一个状态机（`Welcome → Intro → LandSelect → LandParams → PlantSelect → Confirm → FarmStage(1..5) → Analyze → Revenue`），12 屏都是这个状态机的实例。
4. **场景与机器人。** 玉米田做成网格（每个格子记录"是否已探测"），机器人球形触发器进格即计数；自动巡航按 S 形路点走未访问格；第三人称相机用简单的跟随+旋转。
5. **最后接表现。** 玉米三档贴图、房车开合动画（模型已带独立开合动作）、地形模型替换。

### 技术口径

- **UI**：项目已含 `com.unity.ugui` + `com.unity.textmeshpro` 3.0.7。**注意中文字体**——TMP 默认字体不含中文字形，需要做中文字体资源（图集），这件事建议提前安排，它是"看起来没做但卡一天"的典型。
- **输入**：明确用哪套 Input 方案，写进文档，避免两人各写一套。
- **不要硬编码**：文档里大量数值如果散落在几十个 MonoBehaviour 里，第二版一定会失控。

### 建议产出的文档（补齐当前缺口）

- `Assets/README` 或 `Docs/` 下补一份 **《数值规格书》**：单位、量纲、Ymax、经济参数、复合肥折算、噪声模型。
- 一份 **《界面状态机图》**：把 12 屏的转移条件画成图（含返回按钮的目标屏），避免实现时各人理解不同。
- 这份《Unity界面.docx》建议**改名 + 版本号**（如 `Docs/设计说明_界面与数值_v1.0.docx`），并在文档开头加一段"本版已实现 / 未实现"的状态表——现在"暂时完成一部分功能"到底完成了什么，文档里看不出来。

## 八、总体评价

**架构合格，数值待补，玩法偏演示。**

作为第一版方案，它的**流程完整度、UI 一致性、数据可计算性**三项都在学生项目里属于中上，尤其"把土壤、水肥、产量串成一条能算的链"这件事已经做到了 70%。美术资源也基本齐备，落地路径清晰。

真正的风险不在界面，而在两处：
1. **数值闭环没有闭合**——Ymax、单位、复合肥折算、经济层缺失，四个静态指标悬空，且"照建议做指标不变化"使模拟失去动态；
2. **玩法是"照着系统给的答案填"**——玩家没有真实决策空间，这会让"自主调整管理方案"的宣传语和实际体验对不上。

这两个问题都在**写代码之前**解决最便宜。建议后续第一步就是拿这份文档跟策划过一遍第六节的 12 个问题，把数值规格书定下来，然后从纯 C# 数值内核开始动工。
