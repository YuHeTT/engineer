### D2【挂起】Fwater 的单阶段公式 Fw,s

#### 文档现状

```
[245] Fwater：全生育期平均水分系数，**由玩家每阶段灌溉量计算**(因系统自动推荐最优灌溉量)
[246] Fwater = (α1·Fw,s1 + α2·Fw,s2 + α3·Fw,s3 + α4·Fw,s4) / 4
[247] α1=0.2, α2=0.2, α3=0.4, α4=0.2
[248] Fw,s1=1, Fw,s2=1, Fw,s3=1, Fw,s4=1
[249] Fwater=1
```

#### 已确认的理解

- `Fwater` **不是常量**，而是玩家灌溉决策的函数
- [248] 那四个 `=1` 是**"玩家照抄系统推荐灌溉量"时的取值**，[249] 的 `Fwater=1` 是由此得出的**结论**
- 这与文档引用的 **[7] Jensen 乘法水分生产函数**一致（α3=0.4 即生殖期敏感权重）

#### 代码现状（2026-10-16 更新）

公式链已经统一成一条，收益屏、批量验证窗口、自检工具都只读同一份结果：

```
Simulation.Revenue() → RevenueReport.Create() → YieldModel.Compute()
```

`Ffert` / `Fwater` / `Sstatic` / `Y` 由 `YieldModel` 一次算完塞进报告，
**任何地方都不许再自己拼公式**（见 `YieldModel.cs` 顶部与 `RevenueReport.cs` 顶部注释）。

因此 D2 的接入点已经收敛成两个地方：

- `YieldModel.SimplifiedWaterFactors()` —— 现在返回全 1（= 文档 [248] 的取值）
- `Simulation._stageWaterFactors`（配 `StageWaterFactors()` 读数）—— 将来按灌溉量填 Fw,s 的地方

`Alpha = {0.2,0.2,0.4,0.2}`、`UseWeightedWater = true` 与 **Σα 归一化**已就位：
`Fw,s` 全 1 时 `Fwater` 恰好 = 1（与 [249] 一致），已被自检工具钉住。

> **一处文档不一致**：[246] 写 `÷4`，但 [247] 的 α 和为 1，按字面代入 [248] 会得 0.25，
> 与 [249] 的 `Fwater = 1` 矛盾。实现按 Σα 归一化；若策划确认要按字面 ÷4，
> 改 `YieldModel.WaterFactor()` 最后一行即可。
>
> **另外**：`Ffert` 现在只对"已结算阶段"求平均（未结算阶段不会被按 0 摊进去），
> 报告里用 `CommittedCount` / `IsPartial` 标明是中间态。

**回归方式**：菜单 **Engineer / 收益链路自检**（`RevenueChainCheck.Run`），
覆盖公式一致性、部分结算、α 加权取值、报告快照四组共 18 项。

#### 一个更深的设计问题（一并记录）

若"系统已推荐最优灌溉量"，玩家**照抄就永远 `Fwater=1`** ——
那 `Fwater` 对收益**没有任何区分度**，玩家也没有动机不照抄。

目前数值模型里**没有水分成本项**（你已说明：Demo 阶段成本系统未设计）。
所以有两种可能：

| 路线 | 说明 |
|---|---|
| **A. 给灌溉加成本** | 让玩家在"多灌溉→产量高但成本高"之间权衡，`Fwater` 才有意义 —— 属玩法扩展，Demo 可能不做 |
| **B. 保持 `Fwater = 1`** | 但要**在文档与 UI 里写明这是简化**，避免被评委问到时说不清 |

**建议**：Demo 阶段走 B，并在收益屏注明"水分胁迫本版按最优灌溉简化处理"。
