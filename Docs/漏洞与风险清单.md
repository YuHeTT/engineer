# 漏洞与风险清单

> 本文汇总当前**已知的漏洞、设计缺陷与工程风险**，按"必须修 / 应该修 / 建议改"分级。
> 状态：`Assets/Scripts/` 框架已建立，Core 独立编译通过，冒烟测试 32 项全绿。
>
> 相关：[数值内核代码框架说明.md](数值内核代码框架说明.md)、[数值模拟验证记录.md](数值模拟验证记录.md)

---

## 一、必须修（会直接导致功能不对）

### 🔴 G1 · 静态指标默认永远是范围下界

**严重程度：高。会让文档里"随机生成"的设计完全失效。**

`Simulation.Initialize(userInput, rng = null)` 的 `rng` 是可选参数，而
`SoilGenerator.Generate()` 在 `rng == null` 时会**取范围下界**：

```csharp
soil[range.Metric] = rng != null ? range.Sample(rng) : range.Min;
```

**实测证据**（冒烟测试第 5 组输出）：

```
起点土壤: pH=6.90 OM=21.50 N=100.00 P=16.50 K=145.00 |
          Eh=400.0 BaseIon=7.0 As=5.00 Hg=0.030
```

`Eh=400 / BaseIon=7 / As=5 / Hg=0.03` **正好是文档 TABLE 2 的下限**。

**后果**：如果 UI 层调用时不传 `rng`（很容易忘），四个静态指标每局都一样，
文档"根据下表随机生成"和策划"初始的随机没有意义"的诉求都落空，而且**不报错、看不出来**。

**修法**：`rng = null` 时自动 `new System.Random()`，显式传 null 才走确定性路径。

---

### 🔴 G2 · 文档推荐规则表不完备（S2 / S4 各 8 万余组无定义）

**严重程度：高。但已有兜底，不会崩，只是建议不是策划定义的。**

阈值采样 25 万组 × 4 阶段实测的空洞分布：

| 阶段 | 无精确匹配组数 | 根因 |
|---|---|---|
| S1 | 16,384 | 行1 要"任意项 `<0.6`"、行2 要"全部 `≥0.6` 且 `≥3项≥0.8`"，两者之间有夹缝 |
| **S2** | **81,920** | **只判定 fN**。fN 高但 fP / fK 低时，三条规则全不成立 |
| S3 | 3,072 | 行1 只看 N/P/K，行3 要"全部 ≥0.8"。pH / OM 低但 N/P/K 都高时无匹配 |
| **S4** | **81,920** | **只判定 fK**，问题同 S2 |

**当前兜底**：`PlanTable` 三级匹配 —— 精确匹配 → `IsFallback` 规则（"缺什么补什么"）→ 最高优先级。
保证 `Match()` 永不返回 null，且降级合理（S2 缺磷会给出"氮肥为主 + 磷肥"）。

**但仍需策划补规则**，否则大量输入会走到未经定义的建议上。建议补：

```
S2 增加：fP < 0.6 的分支（补磷）
S2 增加：fK < 0.6 的分支（补钾）
S4 增加：fN / fP 偏低的分支
S1 明确：全部 ≥0.6 但 <3 项 ≥0.8 时走哪条（目前兜底走行1）
```

`LastMatchUsedFallback` 已暴露出来，UI 可以据此提示"该情况文档未定义"。

### 🔴 G3 · 模型是"达标制"，多施肥没有反馈

**严重程度：高。这解释了你反馈的"结果比较固定"。**

适宜度函数是**平台型**：只要指标落在最优区间内，适宜度恒等于 **1.0**。
于是 `Ffert,stage = 1×1×1×1×1 = 1.0`，再多施也没有提升空间。

**实测**（照抄建议为基准）：

| 施肥倍率 | 0.5x | 1.0x | 1.5x | 2.0x | 3.0x |
|---|---|---|---|---|---|
| 产量 / Ymax | 92.06% | 93.75% | **93.75%** | **93.75%** | **93.75%** |

**1.5 倍到 3 倍，结果一模一样。** 玩家多施肥完全没有反馈。

**修法**（择一）：
1. 把适宜度从"平台型"改成**钟形**（最优区间是个尖峰而不是一段平地）
2. 给过量施肥加**显式惩罚项**（当前只靠 0.2 保底，太钝）
3. `Ffert` 改用几何平均，让"某阶段崩了"不被其他阶段平均掉

---

### 🔴 G4 · pH 会净下降（与"有机肥改良酸性土"的意图相反）

**严重程度：中高。让"改土"叙事说不通。**

```
新pH = 当前pH + (6.25 − 当前pH) × 有机肥/80 × 0.1 × 有效水比
                − 0.15 × 氮肥/12 × 有效水比
```

按建议量代入：

| 项 | 算式 | 效果 |
|---|---|---|
| 有机肥项 | `× 80/80 × 0.1` = **+0.100** | 推向 6.25（中和） |
| 氮肥项 | `− 0.15 × 12/12` = **−0.150** | 拉低（酸化） |

**氮肥酸化力度是有机肥中和的 1.5 倍。**

**实测**：起点 pH 6.9000 → 四阶段后 **6.8113**，净降 0.089。

**修法**：把 `pH_NCoef` 从 `0.15` 调到约 `0.05`，**不改代码**（已是配置字段）。
或在 `SimConfig.CreateDefault()` 里改默认值。

---

### 🔴 G5 · 初始区间上沿会让成绩反而变差

**严重程度：中高。玩家"往好里填"会拿低分，演示时一定会被问。**

策划给的输入区间 `pH 5.8~8 / OM 15~28 / N 70~130 / P 8~25 / K 90~200`，
其中几个上沿**刚好落在适宜度的下降段**：

| 指标 | 区间上限 | 落在哪个段 | 该段适宜度 |
|---|---|---|---|
| pH | **8.0** | 7.0–8.5 下降段 | **0.467** |
| 速效氮 | **130** | 110–150 下降段 | **0.600** |

**实测**（照抄建议）：

| 起点 | 平均 Ffert | 产量 / Ymax |
|---|---|---|
| 区间下界 | 0.4497 | 44.97% |
| 区间中值 | 0.9375 | **93.75%** |
| 区间上界 | 0.1906 | **19.06%** |

**修法**：把输入区间上沿收进最优区间内，例如 `pH 5.8~7.0`、`N 70~110`。

### ✅ G6 · 已修复：外部编译验证已扩展到三个程序集

**原问题**：本轮出现了这个报错，而我在 Unity 外部只验证了 `Core`，所以没能提前发现：

```
Assets\Scripts\Editor\BatchValidationWindow.cs(35,17): error CS0246:
The type or namespace name 'SimConfigAsset' could not be found
```

**真实根因（比一开始判断的更简单）**：
`BatchValidationWindow.cs` 只写了 `using Engineer.Core;`，**漏了 `using Engineer.Config;`** ——
`SimConfigAsset` 在 `Engineer.Config` 命名空间里。
第一次修复时我改了 asmdef 加上 `Engineer.Config` 引用，但**漏了 using**，所以报错依旧。

**已修复**：
1. `BatchValidationWindow.cs` 补上 `using Engineer.Config;`
2. 新增 `Temp/compile-all.ps1`，在 Unity 外部按依赖顺序编译三个程序集：

```
=== 编译 Engineer.Core ===      源文件: 20 个   ★ 通过 (33.0 KB)
=== 编译 Engineer.Config ===    源文件: 1 个    ★ 通过 (6.5 KB)
=== 编译 Engineer.Editor ===    源文件: 1 个    ★ 通过 (14.0 KB)
全部程序集编译通过。
  · Engineer.Core 未使用任何 Unity 参考程序集 -> 零依赖成立
```

它同时提供 `UnityEngine.dll` / `UnityEditor.dll` 参考程序集，所以**漏 asmdef 引用、漏 using、
类型名写错**这类问题都能在启动 Unity 之前抓到。

**遗留限制**：`Config` / `Editor` 只能验证到"可编译"。
它们的**运行时行为**仍需在 Unity 内确认 —— `Engineer.Config` 继承 `ScriptableObject`、
引用 `UnityEngine.CoreModule`，纯 .NET 宿主加载不了（已验证过，属环境限制而非代码问题）。
建议后续用 Unity Test Framework 补齐（见 [脚本使用与集成指南.md](脚本使用与集成指南.md) 第 5.4 节）。

## 二、应该修（影响正确性或可维护性）

### 🟠 H1 · 适宜度被重复计算

`Simulation.Commit()` 内部算了 3 次适宜度：

```csharp
var fit = SuitabilityResult.From(soilBefore, _config);   // 1
...
var rec = _planTable.Match(stage, fit);                  // 用了局部 fit，正确
```

但外部代码如果这样写就会重复：

```csharp
var fit = sim.Evaluate();          // 算 1 次
var rec = sim.Recommend();         // 内部又调 Evaluate()，算第 2 次
var grow = sim.CurrentGrowth();    // 再调 Evaluate()，算第 3 次
```

**修法**：`Simulation` 缓存当前阶段的 `SuitabilityResult`，在 `Commit()` 时失效。
或者至少提供 `EvaluateOnce()` 语义并在文档里写清楚。

---

### 🟠 H2 · 玩家输入没有边界校验

`FertilizerApplication` 允许负数。文档没写水肥量的上下限，但：

- 玩家输入 `-100` 会得到荒谬结果（负施肥反而"改良"土壤）
- 输入 `1e9` 会让指标爆表

**修法**：在 `SimConfig` 加 `InputLimits`（水肥各自的 min/max），`Simulation.Commit()` 入口做 `Clamp`。
默认可以给一个宽松但安全的范围（如 0 ~ 建议量的 5 倍）。

---

### 🟠 H3 · `Core/Config/` 目录名与 `Engineer.Config` 程序集容易混淆

重组后 `Core` 里有个 `Config/` 子目录（放 `SimConfig.cs` / `SimConfigParts.cs`），
而同一个工程里还有个 `Engineer.Config` 程序集。

**目前不冲突**（目录名不产生命名空间，两边都是 `Engineer.Core` 命名空间），
但团队协作时会有人搞混"改哪个文件"。

**修法**：把 `Core/Config/` 改名为 `Core/Settings/`，或把程序集改名。

---

### 🟠 H4 · `SoilState` 是引用类型，存在状态共享风险

`StageResult.SoilBefore` 持有的是当时的 `_soil` 引用，而不是副本。
目前 `SoilAdvance.Advance()` 会 `new SoilState(current)` 所以没出问题，
但将来如果有人直接改 `result.SoilBefore`，会同时改到 `Simulation` 的内部状态。

**修法**：`StageResult.SoilBefore` 存 `Clone()`；或把 `SoilState` 改成 `struct`（但要评估装箱与拷贝成本）。

---

### 🟠 H5 · `PlanTable` 在构造时快照了配置

`PlanTable` 构造时把 `PlanRules` 拷进 `_byStage` 并排序。
如果之后改了 `SimConfig.PlanRules`，**`PlanTable` 不会感知**。

**目前没问题**（`Simulation` 在构造时创建 `PlanTable`，配置之后不再改）。
**修法**：在 `PlanTable` 文档里写清"配置必须在构造前定型"，或加一个 `Rebuild()`。

---

### 🟠 H6 · 经济层完全缺失

文档说"输出 Y 作为最终收益"，但：

- `Y` 的单位是 kg/亩（**产量**），不是钱
- 界面叫"收益计算"，却没有玉米单价、肥料成本、灌溉成本

`RevenueReport` 里已预留 `PricePerKg` / `TotalCost` / `GrossIncome` / `NetIncome`，
但**没有数据来源**。

**修法**：需要策划给单价与各项成本。这也是竞赛评审会关注的点（"收益"体现在哪）。

---

## 三、建议改（健壮性与长期可维护性）

### 🟡 I1 · 没有接口层隔离 UI 与数据

UI 直接持有 `Simulation`，可以访问 `CurrentSoil`（返回内部引用）。
虽然文档写了"只读语义"，但**代码上没有强制**。

**修法**：给 `Simulation` 加只读接口 `ISimulationView`（只有 `Evaluate` / `Recommend` / `CurrentSoil` 的只读访问），
UI 层依赖接口而不是具体类。这样也方便写 UI 的假数据测试。

---

### 🟡 I2 · 检测数据没有误差机制

文档的设计意图是"原数据可能不准，需要机器人探测"，但目前：

- 探测值 = 真实值（没有误差）
- `SoilGenerator` 生成的静态指标在后续阶段不变

如果探测值等于真值，**"更新数据"这一步没有任何信息增益**，玩家只是多点两下按钮。

**修法**（设计层面）：探测值加一个**随覆盖率收敛的随机误差** —— 覆盖 50% 时误差 ±15%，
覆盖 100% 时误差 0。这样"多跑一会儿机器人"才有意义。
这需要策划确认，属于**未设计**而非 bug。

---

### 🟡 I3 · 阶段 5（收获期）没有任何数值行为

`Stage.Done` 之后 `Commit()` 返回 null。收获期在 UI 上是一个界面，但：

- 没有"收获期数据"（文档说收获期要显示全部数据）
- 收获期与 S4 共用贴图（文档明确说了，OK）

**修法**：`Simulation` 加一个 `HarvestSnapshot()` 返回最终状态，供收获期界面显示。

---

### 🟡 I4 · 没有存档 / 回放能力

Core 是纯数据，理论上是可序列化的，但**没有实现**：

- `SuitabilityCurve` / `PlanCondition` / `PlanRule` 里有数组和引用，`JsonUtility` 处理不了循环引用
- `StageResult` 持有 `SoilState` 引用

**修法**：如果需要存档，写一个独立的 DTO 层做映射，而不是直接序列化 Core 对象。
目前阶段不需要，但要**知道这个限制**，避免后期想在 Core 上直接挂 `JsonUtility` 结果踩坑。

---

### 🟡 I5 · 没有日志 / 诊断通道

`Core` 里没有任何输出机制（这是对的，因为它不能依赖 `Debug.Log`）。
但调试时看不到内部状态。

**建议**：提供一个 `ISimLogger` 接口（可选注入），或者靠 `Simulation.DumpHistory()` 现有的文本导出。
目前 `DumpHistory()` 够用。

---

### 🟡 I6 · 批量验证窗口的覆盖性检查会卡界面

`CheckCoverage` 是 O(n⁵)。默认采样 12 个值 → `12⁵ = 248,832` 组 × 4 阶段 ≈ **100 万次判定**。
在编辑器里点按钮会卡住几秒。

**修法**：放到后台线程，或降低采样档数，或加进度条。
目前可以接受（不常点），但团队里有人会以为 Unity 卡死了。

## 四、设计层面尚未定义的问题（需要策划）

这些**不是代码 bug**，而是需求本身还缺定义。列出来避免实现时才吵：

| # | 问题 | 影响 |
|---|---|---|
| D1 | **"原数据 / 探测数据 / 真实值"三层关系** | 更新数据后原值算不算真实值？不点更新直接分析用哪套？ |
| D2 | **探测误差模型** | 见 I2。没有误差则探测机制无意义 |
| D3 | **巡航完成的判定标准** | 必须 100% 覆盖还是 95%？手动模式绕不完整块田会不会卡死？ |
| D4 | **手动操控的相机视角** | 文档写"第三人称"，但概念图是俯视——两者不是一回事 |
| D5 | **返回上一步的数据保留策略** | 返回后重进，填过的水肥和探测数据是保留还是清零？ |
| D6 | **第一、二、三、四、五阶段的编号** | 文档 `S1~S4` 与"阶段一~五"两套编号，代码已统一为 `Stage.S1~S4 + Done` |
| D7 | **S5 界面上的"机器人检测"按钮** | 你确认 S5 不需操作，但那颗按钮在概念图上还在 |
| D8 | **四个静态指标完全不参与计算** | 策划已确认，但"初始随机"因此没有玩法意义（见 G1 之外的深层问题） |
| D9 | **地形差异化** | 四套地形目前只有文案和模型，没有数值差异（你已确认 v1 只做平川台） |
| D10 | **作物差异化** | 三种作物没有独立曲线与推荐表（你已确认 v1 只做玉米） |

## 五、修复优先级建议

按"改动成本 ÷ 收益"排序：

| 优先级 | 事项 | 成本 | 收益 |
|---|---|---|---|
| **P0** | G1 静态指标随机（改 1 行） | 极低 | 让文档的随机设计真正生效 |
| **P0** | G6 扩展编译验证到三个程序集 | 低 | 避免再出现 asmdef 漏引用这类错 |
| **P0** | 反馈 G2 规则空洞给策划 | 低 | S2/S4 各 8 万组输入走的是未定义建议 |
| **P1** | G4 pH 系数（改配置 1 个数） | 极低 | 让"有机肥改土"叙事成立 |
| **P1** | G5 收窄输入区间上沿 | 极低 | 消除"填越高分越低" |
| **P1** | H2 输入边界校验 | 低 | 防止荒谬输入 |
| **P2** | G3 适宜度改钟形 | 中 | 解决"结果固定"的根本问题 |
| **P2** | H1 适宜度缓存 | 低 | 性能与一致性 |
| **P2** | H6 补经济层参数 | 需策划 | 竞赛"收益"的说服力 |

## 六、一句话总结

**代码能跑、逻辑经得起验证（32 项测试全绿），但存在 6 个必须修的问题**：

1. **静态指标默认永远是下界** —— 1 行代码，但让"随机生成"完全失效（最该先修）
2. **文档规则表不完备** —— S2/S4 各 8 万余组输入无定义，已兜底但需策划补规则
3. **模型是达标制** —— 施肥 1.5x 到 3x 结果完全相同，这是"结果固定"的根因
4. **pH 净下降** —— 有机肥中和 0.1 弱于氮肥酸化 0.15，改 1 个配置数就能修
5. **区间上沿反而更差** —— 19.06% vs 44.97%，收窄区间即可
6. **只有 Core 被编译验证** —— Config / Editor 漏引用已经踩到过一次

其中 **1、4、5 都是改一个数或一行代码**，却直接影响演示效果，建议优先处理。
