# 漏洞与风险清单

> 本文汇总当前**已知的漏洞、设计缺陷与工程风险**，按"必须修 / 应该修 / 建议改"分级。
> 状态：`Assets/Scripts/` 框架已建立，Core 独立编译通过，冒烟测试 42 项全绿。
>
> 相关：[数值内核代码框架说明.md](数值内核代码框架说明.md)、[数值模拟验证记录.md](数值模拟验证记录.md)

## 一、必须修（会直接导致功能不对）

### 🔴 G1 · 静态指标默认永远是范围下界

**严重程度：高。会让文档里"随机生成"的设计完全失效。**

`Simulation.Initialize(userInput, rng = null)` 的 `rng` 是可选参数，而
`SoilGenerator.Generate()` 在 `rng == null` 时会**取范围下界**：

```csharp
soil[range.Metric] = rng != null ? range.Sample(rng) : range.Min;
```

**实测证据**（冒烟测试第 5 组输出）：

```
起点土壤: pH=6.90 OM=21.50 N=100.00 P=16.50 K=145.00 |
          Eh=400.0 BaseIon=7.0 As=5.00 Hg=0.030
```

`Eh=400 / BaseIon=7 / As=5 / Hg=0.03` **正好是文档 TABLE 2 的下限**。

**后果**：如果 UI 层调用时不传 `rng`（很容易忘），四个静态指标每局都一样，
文档"根据下表随机生成"和策划"初始的随机没有意义"的诉求都落空，而且**不报错、看不出来**。

**修法**：`rng = null` 时自动 `new System.Random()`，显式传 null 才走确定性路径。

---

### 🔴 G2 · 文档推荐规则表不完备（S2 / S4 各 8 万余组无定义）

**严重程度：高。但已有兜底，不会崩，只是建议不是策划定义的。**

阈值采样 25 万组 × 4 阶段实测的空洞分布：

| 阶段 | 无精确匹配组数 | 根因 |
|---|---|---|
| S1 | 16,384 | 行1 要"任意项 `<0.6`"、行2 要"全部 `≥0.6` 且 `≥3项≥0.8`"，两者之间有夹缝 |
| **S2** | **81,920** | **只判定 fN**。fN 高但 fP / fK 低时，三条规则全不成立 |
| S3 | 3,072 | 行1 只看 N/P/K，行3 要"全部 ≥0.8"。pH / OM 低但 N/P/K 都高时无匹配 |
| **S4** | **81,920** | **只判定 fK**，问题同 S2 |

**当前兜底**：`PlanTable` 三级匹配 —— 精确匹配 → `IsFallback` 规则（"缺什么补什么"）→ 最高优先级。
保证 `Match()` 永不返回 null，且降级合理（S2 缺磷会给出"氮肥为主 + 磷肥"）。

**但仍需策划补规则**，否则大量输入会走到未经定义的建议上。建议补：

```
S2 增加：fP < 0.6 的分支（补磷）
S2 增加：fK < 0.6 的分支（补钾）
S4 增加：fN / fP 偏低的分支
S1 明确：全部 ≥0.6 但 <3 项 ≥0.8 时走哪条（目前兜底走行1）
```

`LastMatchUsedFallback` 已暴露出来，UI 可以据此提示"该情况文档未定义"。

### 🔴 G3 · 模型是"达标制"，多施肥没有反馈

**严重程度：高。这解释了你反馈的"结果比较固定"。**

适宜度函数是**平台型**：只要指标落在最优区间内，适宜度恒等于 **1.0**。
于是 `Ffert,stage = 1×1×1×1×1 = 1.0`，再多施也没有提升空间。

**实测**（照抄建议为基准）：

| 施肥倍率 | 0.5x | 1.0x | 1.5x | 2.0x | 3.0x |
|---|---|---|---|---|---|
| 产量 / Ymax | 92.06% | 93.75% | **93.75%** | **93.75%** | **93.75%** |

**1.5 倍到 3 倍，结果一模一样。** 玩家多施肥完全没有反馈。

**修法**（择一）：
1. 把适宜度从"平台型"改成**钟形**（最优区间是个尖峰而不是一段平地）
2. 给过量施肥加**显式惩罚项**（当前只靠 0.2 保底，太钝）
3. `Ffert` 改用几何平均，让"某阶段崩了"不被其他阶段平均掉

### 🔴 G4 · pH 会净下降（与"有机肥改良酸性土"的意图相反）

**严重程度：中高。让"改土"叙事说不通。**

```
新pH = 当前pH + (6.25 − 当前pH) × 有机肥/80 × 0.1 × 有效水比
                − 0.15 × 氮肥/12 × 有效水比
```

按建议量代入：

| 项 | 算式 | 效果 |
|---|---|---|
| 有机肥项 | `× 80/80 × 0.1` = **+0.100** | 推向 6.25（中和） |
| 氮肥项 | `− 0.15 × 12/12` = **−0.150** | 拉低（酸化） |

**氮肥酸化力度是有机肥中和的 1.5 倍。**

**实测**：起点 pH 6.9000 → 四阶段后 **6.8113**，净降 0.089。

**修法**：把 `pH_NCoef` 从 `0.15` 调到约 `0.05`，**不改代码**（已是配置字段）。
或在 `SimConfig.CreateDefault()` 里改默认值。

---

### 🔴 G5 · 初始区间上沿会让成绩反而变差

**严重程度：中高。玩家"往好里填"会拿低分，演示时一定会被问。**

策划给的输入区间 `pH 5.8~8 / OM 15~28 / N 70~130 / P 8~25 / K 90~200`，
其中几个上沿**刚好落在适宜度的下降段**：

| 指标 | 区间上限 | 落在哪个段 | 该段适宜度 |
|---|---|---|---|
| pH | **8.0** | 7.0–8.5 下降段 | **0.467** |
| 速效氮 | **130** | 110–150 下降段 | **0.600** |

**实测**（照抄建议）：

| 起点 | 平均 Ffert | 产量 / Ymax |
|---|---|---|
| 区间下界 | 0.4497 | 44.97% |
| 区间中值 | 0.9375 | **93.75%** |
| 区间上界 | 0.1906 | **19.06%** |

**修法**：把输入区间上沿收进最优区间内，例如 `pH 5.8~7.0`、`N 70~110`。

## 二、应该修（影响正确性或可维护性）

### 🟠 H1 · 适宜度被重复计算

`Simulation.Commit()` 内部算了 3 次适宜度：

```csharp
var fit = SuitabilityResult.From(soilBefore, _config);   // 1
...
var rec = _planTable.Match(stage, fit);                  // 用了局部 fit，正确
```

但外部代码如果这样写就会重复：

```csharp
var fit = sim.Evaluate();          // 算 1 次
var rec = sim.Recommend();         // 内部又调 Evaluate()，算第 2 次
var grow = sim.CurrentGrowth();    // 再调 Evaluate()，算第 3 次
```

**修法**：`Simulation` 缓存当前阶段的 `SuitabilityResult`，在 `Commit()` 时失效。

**✅ 已修复**：`Simulation` 增加 `_cachedFit` 字段，`Evaluate()` 首次计算后缓存；
`Initialize` / `Reset` / `Commit` 都会调 `InvalidateCache()`。
冒烟测试 2 项断言守着（同一对象、提交后失效）。

---

### 🟠 H2 · 玩家输入没有边界校验

`FertilizerApplication` 允许负数。文档没写水肥量的上下限，但：

- 玩家输入 `-100` 会得到荒谬结果（负施肥反而"改良"土壤）
- 输入 `1e9` 会让指标爆表

**✅ 已修复**：新增 `SimConfigParts.InputLimits`（配置类）+ `SimConfig.Inputs` 字段。
`Simulation.Commit()` 在演算前先钳制，`StageResult.Applied` 存的是**钳制后**的投入。

默认策略（**只做防护，不做设计约束**）：

| 项 | 默认值 |
|---|---|
| 下限 | `0`（不允许负投入） |
| 灌溉上限 | 建议灌溉量 × `5` |
| 肥料上限 | 对应建议量 × `5` |
| 建议量为 0 时的回退上限 | `1000`（绝对天花板） |
| 开关 | `Enabled`，关掉后原样放行（调试对比用） |

**为什么用"建议量的倍数"而不是硬编码数字**：建议量本身就是该阶段合理的量级，
倍数比绝对值更稳定，也不会和策划后续调整建议量脱节。
如果策划将来要规定"每亩最多施 X kg"这类**玩法约束**，应该改 `AbsoluteMax*` 而不是倍数。

冒烟测试 3 项断言守着（负数归零、超大值钳到上限、倍数规则生效）。

---

### 🟠 H3 · `Core/Config/` 目录名与 `Engineer.Config` 程序集容易混淆

重组后 `Core` 里有个 `Config/` 子目录（放 `SimConfig.cs` / `SimConfigParts.cs`），
而同一个工程里还有个 `Engineer.Config` 程序集。

**✅ 已修复**：`Core/Config/` → **`Core/Settings/`**。
目录的 `.meta` 也一起改名，**保留了原 GUID**，所以不会有引用断裂。

---

### 🟠 H4 · `SoilState` 是引用类型，存在状态共享风险

`StageResult.SoilBefore` 持有的是当时的 `_soil` 引用，而不是副本。
将来如果有人直接改 `result.SoilBefore`，会同时改到 `Simulation` 的内部状态。

**✅ 已修复**：`Simulation.Commit()` 改为存 `_soil.Clone()`。
冒烟测试 2 项断言守着（不是同一对象、改快照不影响内部状态）。

> 没有把 `SoilState` 改成 `struct` —— 它会被四处传递，值语义会导致大量隐式拷贝，
> 而且容易在写法上误导（`state.pH = 1` 改的是副本，不报错但没效果）。
> 保持引用类型 + 明确快照点，比换 struct 更清晰。

---

### 🟠 H5 · `PlanTable` 在构造时快照了配置

`PlanTable` 构造时把 `PlanRules` 拷进 `_byStage` 并排序。
如果之后改了 `SimConfig.PlanRules`，**`PlanTable` 不会感知**。

**✅ 已处理（改为显式契约）**：这是刻意的设计（避免每次匹配都排序），
保留行为不动，但在构造函数上写了明确警告：

> 配置定型之后再构造 `PlanTable`。运行中要热改规则，就重新 `new PlanTable`。
> `Simulation` 在构造函数里创建它，所以"改配置 = 重新 new Simulation"。
**保留（需策划）**：`RevenueReport` 里已预留 `PricePerKg` / `TotalCost` / `GrossIncome` / `NetIncome`，
但**没有数据来源**。需要策划给玉米单价与各项成本。
这也是竞赛评审会关注的点（"收益"体现在哪）。

## 三、建议改（健壮性与长期可维护性）

### 🟡 I1 · 没有接口层隔离 UI 与数据

UI 直接持有 `Simulation`，可以访问 `CurrentSoil`（返回内部引用）。
虽然文档写了"只读语义"，但**代码上没有强制**。

**✅ 已修复**：新增 `Core/Simulate/ISimulationView.cs`。
`Simulation` 实现该接口，并暴露 `View` 属性。

```csharp
// 场景启动时
var sim = new Simulation(cfg);
screen.Bind(sim.View);        // 只把只读视图交给 UI

// UI 内部：_view 的类型是 ISimulationView，编译期就调不到 Commit/Initialize/Reset
```

好处：编译期挡住误调写操作；写 UI 测试时可以塞假实现，不必真跑数值。
冒烟测试 2 项断言守着。

> 注：`CurrentSoil` 仍返回内部引用（只读语义），这是刻意的 ——
> 拷贝一份给 UI 展示没必要，而且会让"当前土壤"和"刚提交的土壤"
> 出现两个不同对象，反而容易搞混。约定：要改先 `Clone()`。

---

### 🟡 I2 · 检测数据没有误差机制

文档的设计意图是"原数据可能不准，需要机器人探测"，但目前：

- 探测值 = 真实值（没有误差）
- `SoilGenerator` 生成的静态指标在后续阶段不变

如果探测值等于真值，**"更新数据"这一步没有任何信息增益**，玩家只是多点两下按钮。

**修法**（设计层面）：探测值加一个**随覆盖率收敛的随机误差** —— 覆盖 50% 时误差 ±15%，
覆盖 100% 时误差 0。这样"多跑一会儿机器人"才有意义。
这需要策划确认，属于**未设计**而非 bug。

---

### 🟡 I3 · 阶段 5（收获期）没有任何数值行为

`Stage.Done` 之后 `Commit()` 返回 null。收获期在 UI 上是一个界面，但：

- 没有"收获期数据"（文档说收获期要显示全部数据）
- 收获期与 S4 共用贴图（文档明确说了，OK）

**修法**：`Simulation` 加一个 `HarvestSnapshot()` 返回最终状态，供收获期界面显示。

---

### 🟡 I4 · 没有存档 / 回放能力

Core 是纯数据，理论上是可序列化的，但**没有实现**：

- `SuitabilityCurve` / `PlanCondition` / `PlanRule` 里有数组和引用，`JsonUtility` 处理不了循环引用
- `StageResult` 持有 `SoilState` 引用

**修法**：如果需要存档，写一个独立的 DTO 层做映射，而不是直接序列化 Core 对象。
目前阶段不需要，但要**知道这个限制**，避免后期想在 Core 上直接挂 `JsonUtility` 结果踩坑。

---

### 🟡 I5 · 没有日志 / 诊断通道

`Core` 里没有任何输出机制（这是对的，因为它不能依赖 `Debug.Log`）。
但调试时看不到内部状态。

**建议**：提供一个 `ISimLogger` 接口（可选注入），或者靠 `Simulation.DumpHistory()` 现有的文本导出。
目前 `DumpHistory()` 够用。

---

### 🟡 I6 · 批量验证窗口的覆盖性检查会卡界面

`CheckCoverage` 是 O(n⁵)。默认采样 12 个值 → `12⁵ = 248,832` 组 × 4 阶段 ≈ **100 万次判定**。

**✅ 已优化**：`CheckCoverage` 增加 `steps` 参数，支持降采样，
并且降采样时**始终保留阈值本身（0.6 / 0.8）**——边界才是空洞所在，不能丢。

- `CheckCoverage()` — 完整 12 档（约 25 万组）
- `CheckCoverage(8, out report)` — 8 档（约 3.3 万组），快约 7 倍
- `SimConfig.Validate` 内部用 **8 档**，所以校验不再卡

实测 8 档与 12 档**结论一致**（都判定为存在空洞）。冒烟测试 1 项断言守着。
